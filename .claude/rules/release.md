# Release Workflow

## Branching

**Trunk-based development.** `main` is always releaseable.

- Feature work in short-lived branches: `feat/scaffold-use-case`, `fix/bootstrap-patch`
- Squash merge into `main` — keeps history clean and bisectable
- No `develop`, `release/*`, or `hotfix/*` branches
- Release tags (`v0.2.0`) are the only long-lived markers

---

## Commit Convention

All commits must follow **Conventional Commits**:

```
feat: add puerto generate migration command
fix: bootstrap overwrites entity block on second run
docs: update puerto-toml derivation table
chore: upgrade cargo-generate to 0.23
refactor: extract patch_lib_block into own module
test: add idempotency test for use-case generator
```

**Types:** `feat` · `fix` · `docs` · `chore` · `refactor` · `test` · `perf`

`CHANGELOG.md` is generated automatically from these commits via **git-cliff**. Do not write it by hand.

---

## Versioning

Puerto follows **SemVer**. The public API is not just the CLI flags — it includes:

- The generated project structure (file paths, module layout)
- `puerto.toml` schema
- The bootstrap.rs generation contract

| Bump              | When                                                                                                  |
| ----------------- | ----------------------------------------------------------------------------------------------------- |
| `patch` 0.1.**x** | Bug fix in generation, typo in template, bootstrap fix. No change to generated shape.                 |
| `minor` 0.**x**.0 | New command, new flag, new files generated, additive puerto.toml field. Backward-compatible.          |
| `major` **x**.0.0 | Generated file layout change, module rename, puerto.toml incompatible schema change, command removed. |

**While on `0.x.y`**: minor bumps may include breaking changes — this is the convention for pre-1.0 crates. Document all breaking changes in `CHANGELOG.md` under `### Breaking`.

---

## Changelog

Generated by **git-cliff** from conventional commits. Never hand-edited.

```bash
git cliff --unreleased --prepend CHANGELOG.md
```

Structure:

```markdown
## [Unreleased]

## [0.2.0] - 2026-05-01

### Added

### Fixed

### Changed

### Breaking

### Migration Guide ← required for any breaking change
```

The `## Migration Guide` section is **required** for any release that changes:

- Generated file layout
- puerto.toml schema
- Module names visible in generated code

## Release Process

Pushing a `v*` tag publishes: `release.yml` checks the tag matches the version of **every**
published crate (one `[workspace.package] version` in the root `Cargo.toml` — ADR-0017), runs
`make test/full`, then `cargo publish --locked` for the runtime crates first, in dependency order,
then `puerto`:

```
puerto-core → puerto-macros → puerto-web → puerto-sqlx → puerto-events → puerto-kafka → puerto-mail → puerto
```

A crate whose version is already on crates.io is skipped, so publishing by hand first does not
turn the run red. A project generated by `puerto` 0.x asks crates.io for the runtime crates at
0.x: the CLI must never be on crates.io without them.

```bash
# 1. Bump version — once for every crate
#    Edit the root Cargo.toml — [workspace.package] version = "0.x.y", and the same version in
#    every entry of its [workspace.dependencies] (puerto-core, puerto-macros, puerto-web: what
#    the runtime crates depending on them are published against)

# 2. Update changelog (written by hand from the commits since the last release, same format)
#    `git cliff --unreleased --prepend CHANGELOG.md` drafts it when git-cliff is installed

# 3. Verify
make test
make test/full
make test/db
make test/kafka
make test/mail
make lint
make format
cargo package --list -p puerto       # confirm template files are included
cargo publish --dry-run -p puerto-core
cargo publish --dry-run -p puerto-macros
cargo publish --dry-run -p puerto-web
cargo publish --dry-run -p puerto-sqlx
cargo publish --dry-run -p puerto-events
cargo publish --dry-run -p puerto-kafka
cargo publish --dry-run -p puerto-mail
cargo publish --dry-run -p puerto

# 4. Commit, push, tag — the tag publishes
git add -A && git commit -m "chore: release v0.x.y"
git push
git tag -a v0.x.y -m "v0.x.y" && git push origin v0.x.y

# Fallback when the workflow cannot publish — same order:
#   cargo publish -p puerto-core --locked && cargo publish -p puerto-macros --locked \
#     && cargo publish -p puerto-web --locked \
#     && cargo publish -p puerto-sqlx --locked && cargo publish -p puerto-events --locked \
#     && cargo publish -p puerto-kafka --locked && cargo publish -p puerto-mail --locked \
#     && cargo publish -p puerto --locked
```

The landing (`landing/`) is deployed by Vercel on every push to `main` — update its docs in the
release commit's push when the release changes what it describes.

## Pre-Release Checklist

Every release — automated or manual — must pass:

- [ ] `make test` — structural tests pass
- [ ] `make test/full` — generated projects lint clean and internal tests pass ← **most important gate**
      (needs `bun` on `PATH`: the web scenarios install, lint and test the generated frontend)
- [ ] `make test/db` — the `--db` scenario against Postgres
- [ ] `make test/kafka` — the Kafka transport against Redpanda
- [ ] `make test/mail` — the SMTP adapter against Mailpit
- [ ] `make lint` — zero clippy warnings
- [ ] `make format` — no formatting diff
- [ ] `cargo package --list` — template files present in package
- [ ] `cargo publish --dry-run` — no publish errors
- [ ] `CHANGELOG.md` has an entry for this version
- [ ] Every published crate's `Cargo.toml` has `description`, `license`, `repository`, `rust-version`
- [ ] Breaking changes have a `## Migration Guide` in the changelog

## CI/CD

Two GitHub Actions workflows:

**`ci.yml`** — runs on every push and PR:

```
make test
make lint
cargo fmt --check
```

**`ci.yml`** also runs `make test/full` as a separate job.

**`release.yml`** — runs on `v*` tag push:

```
tag == crate version, skip if already on crates.io
make test/full
cargo publish -p puerto --locked
```

Binary distribution via **cargo-dist** is not set up yet — future work.

## Breaking Changes Policy

1. **One-cycle deprecation**: deprecate in `minor`, remove in next `minor`. Print a runtime warning for one release:

   ```rust
   eprintln!("warning: puerto.toml field X is deprecated — use Y instead (see CHANGELOG)");
   ```

2. **Migration guide**: every breaking release must include a `## Migration Guide` section in `CHANGELOG.md` explaining exactly what changed and how to migrate an existing project.

3. **puerto.toml contract**: the schema is the most fragile public contract. If it changes incompatibly, add `schema_version` to the file so Puerto can detect and migrate old projects.

4. **Generated code**: never silently change generated file contents in a patch release. A patch only fixes bugs — it never reorganises what `puerto generate` writes to disk.

## Rust / crates.io Specifics

- **MSRV**: declare `rust-version` in `Cargo.toml`. Test against it in CI with `rustup run <version> cargo check`.
- **Template inclusion**: Puerto embeds its template via `include_dir`. Verify with `cargo package --list` that the embedded bytes are present.
- **Yanking**: use `cargo yank --version X.Y.Z` for broken releases. Never yank a version that working projects depend on.
- **`publish = false`**: set on any workspace member that should not reach crates.io.
- **Cargo.lock**: committed — Puerto is a binary tool, lockfile must be committed.
