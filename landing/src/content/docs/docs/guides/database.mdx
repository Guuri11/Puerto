`puerto nuevo --db` le da a un proyecto una base de datos Postgres con
[SQLx](https://github.com/launchbadge/sqlx): SQL comprobado, escrito en cada repositorio, sin ORM
por medio. Un proyecto sin `--db` guarda sus datos en memoria, que basta para probar una idea y se
pierde al reiniciar.

## Empezar un proyecto con base de datos

<Steps>

1. **Créalo y añade una entidad.**

   ```bash
   puerto nuevo --nombre tienda --db
   cd tienda
   puerto generar scaffold Producto -- nombre:String precio:i64 sku:String!
   ```

   ```txt title="salida (el final)"
   ✓ Migración 'crear_tabla_producto' creada en migraciones/
     Esquema ya escrito; ejecuta: make sqlx/migrate && make sqlx/prepare
   ```

2. **Instala las herramientas, una vez.**

   ```bash
   make setup    # cargo-nextest, sqlx-cli, cargo-audit
   ```

3. **Migra y prepara.** Los dos arrancan antes Postgres en Docker (`docker-compose.yml`,
   `postgres:16`).

   ```bash
   make sqlx/migrate     # aplica las migraciones
   make sqlx/prepare     # escribe .sqlx/, la caché offline de las consultas
   ```

4. **Arráncalo.**

   ```bash
   make run
   ```

   Al arrancar, la API se conecta, ejecuta las migraciones pendientes y sirve. Si la base de
   datos está caída lo dice y sale, en lugar de hacer panic:

   ```txt
   … — ¿está arrancada la base de datos? `make docker-compose/up`
   ```

</Steps>

## Lo que cambia `--db`

| | En memoria | `--db` |
|---|---|---|
| Repositorio | `RepositorioProductoEnMemoria` | `RepositorioProductoPostgres` + `fila.rs` (la fila, `FilaProducto`) |
| Migración | ninguna | `migraciones/…_crear_tabla_producto.sql`, con el esquema escrito desde los campos |
| `/health/ready` | siempre listo | ejecuta `SELECT 1`; `503` cuando Postgres no responde |
| Tests | unitarios | unitarios + tests de integración `#[sqlx::test]` por repositorio |
| Ficheros | | `docker-compose.yml`, `.cargo/config.toml`, `DATABASE_URL` en `.env`, `migraciones/`, el crate `migrador` |

El scaffold escribe la tabla entera, así que no hay nada que rellenar:

```sql title="migraciones/…_crear_tabla_producto.sql"
-- Migración de Puerto: crear_tabla_producto
-- Ejecuta `make sqlx/prepare` después de editar este fichero.

CREATE TABLE productos (
    id UUID PRIMARY KEY,
    nombre TEXT NOT NULL,
    precio BIGINT NOT NULL,
    sku TEXT NOT NULL,
    creado_en TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    actualizado_en TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    borrado BOOLEAN NOT NULL DEFAULT FALSE,
    borrado_en TIMESTAMPTZ
);

CREATE UNIQUE INDEX productos_sku_key ON productos (sku) WHERE borrado = false;
```

El borrado es lógico, así que el índice único es parcial: un producto borrado no sigue ocupando su
SKU ([ADR-0003](/docs/decisions/adr/0003-unique-indexes-are-partial/)).

Una referencia es una clave foránea. `puerto generar scaffold Pedido -- cliente_id:ref:Cliente`
escribe la restricción y un índice para el filtro de la lista:

```sql title="migraciones/…_crear_tabla_pedido.sql (fragmento)"
cliente_id UUID NOT NULL CONSTRAINT pedidos_cliente_id_fkey REFERENCES clientes (id),
-- …
CREATE INDEX pedidos_cliente_id_idx ON pedidos (cliente_id);
```

Que el cliente existe lo comprueba la base de datos, no el caso de uso
([ADR-0022](/docs/decisions/adr/0022-references-are-typed-ids-checked-by-foreign-keys/)).

Las migraciones de todos los contextos viven en un solo directorio, `migraciones/` en la raíz,
porque todas construyen una misma base de datos. El crate `migrador` las embebe al compilar como
`migrador::MIGRADOR` (`sqlx::migrate!("../migraciones")`), y su `build.rs` le dice a Cargo que
recompile cuando cambia ese directorio, así que una migración nueva se ve aunque no cambie ningún
`.rs`. La API ejecuta `MIGRADOR` al arrancar, y todos los tests de Postgres corren sobre él.

## Escribir una migración

```bash
puerto generar migracion anadir_stock_a_productos
```

```txt title="salida"
✓ Migración 'anadir_stock_a_productos' creada en migraciones/
  Edita el fichero y ejecuta: make sqlx/migrate && make sqlx/prepare
```

Puerto escribe el fichero él mismo (este paso no necesita la CLI de `sqlx`), con una versión que es
única aunque sea en el mismo segundo. El comando se rechaza en un proyecto sin `--db`.

<Aside type="caution" title="Lee cada migración">
Una migración falla despacio y cuesta cara: el `AGENTS.md` generado pone las migraciones en el
Tier 1, donde una persona lee el diff entero antes del commit, por muy verdes que estén los tests.
</Aside>

## La caché offline

`query_as!` comprueba cada consulta contra la base de datos **al compilar**. Para que el proyecto
compile sin un Postgres en marcha (en CI, en un clon nuevo), `.cargo/config.toml` pone
`SQLX_OFFLINE=true` y SQLx lee las respuestas de `.sqlx/`. Haz commit de ese directorio.

Tras cambiar una consulta o una migración:

```bash
make sqlx/prepare     # regenera .sqlx/ contra la base de datos en marcha
make sqlx/check       # comprueba que .sqlx/ coincide con las consultas (para CI)
```

`make sqlx/online` y `make sqlx/offline` cambian el modo para trabajar en local.

## Los errores del driver

Cada repositorio Postgres traduce los errores del driver con una sola función,
`mapear_error_sqlx`, de `puerto-sqlx`: un único violado pasa a ser `ErrorRepositorio::Duplicado`
(`409`), y cualquier otra cosa `NoDisponible`. Una fila que el dominio rechaza (datos guardados que
se estropearon) se registra y se devuelve como `DatosInvalidos`, un `500`, nunca un `422` que
culparía a quien llama
([ADR-0015](/docs/decisions/adr/0015-repositories-return-one-repository-error/)).

Una entidad con referencias traduce con `mapear_error_sqlx_con`, que conoce sus claves foráneas por
el nombre de la restricción. Una escritura que nombra un cliente que no existe viola
`pedidos_cliente_id_fkey` y pasa a ser `ErrorRepositorio::ReferenciaInexistente("cliente_id")`,
que el error de la entidad convierte en `pedido.validacion.cliente_id_no_encontrado`, un `422`
sobre ese campo.

## Tests de integración

Cada repositorio Postgres trae tests `#[sqlx::test]`: SQLx crea una base de datos nueva por test,
aplica las migraciones de `migrador::MIGRADOR` y la borra después.

```rust
#[sqlx::test(migrator = "migrador::MIGRADOR")]
async fn deberia_guardar_y_recuperar_por_id(pool: PgPool) {
    // Preparar
    let entidad = sembrar(&pool).await;

    // Actuar
    let encontrado = repositorio_de_prueba(pool)
        .buscar_por_id(entidad.id)
        .await
        .unwrap()
        .unwrap();

    // Comprobar
    assert_eq!(encontrado.id, entidad.id);
    // …
}
```

`sembrar` sale de `infra_producto::pruebas::siembra`, público tras la feature `pruebas`, así que los
tests de un contexto que referencia `Producto` también pueden sembrar uno. Los tests necesitan
`DATABASE_URL` y un Postgres en marcha: `make test/infraestructura`, o `make test` tras
`make docker-compose/up`.

## Mantenimiento

| Comando | Qué hace |
|---|---|
| `make db/arrancar` / `make db/parar` | Arranca o para los contenedores |
| `make db/reiniciar` | Lo borra todo y vuelve a ejecutar las migraciones. Te pide que escribas `DESTRUIR` |
| `make generar/migracion NOMBRE=…` | Lo mismo que `puerto generar migracion` |
