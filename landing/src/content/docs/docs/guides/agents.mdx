Puerto se apoya en una apuesta: **cuanto más estricta la estructura, mejor trabaja un agente dentro
de ella.** Un agente que escribe en un código donde cada proyecto es distinto tiene que adivinar,
y lo que adivina parece razonable. Un agente que escribe en un proyecto Puerto tiene reglas que
puede leer, generadores que escriben el cableado y un compilador que rechaza los errores de
arquitectura con un mensaje preciso.

## Las reglas vienen con el proyecto

Cada proyecto tiene un `AGENTS.md` en la raíz y un `CLAUDE.md` de una línea (`@AGENTS.md`), así que
Claude Code, Codex, Cursor y los demás cargan las mismas instrucciones. `contextos/AGENTS.md`
detalla los cuatro crates de un contexto, y `presentacion/AGENTS.md` el cableado y los binarios;
un proyecto con web añade `web/AGENTS.md`, y uno con eventos `presentacion/worker/AGENTS.md`.
Como todo lo que genera Puerto, están en castellano.

El fichero raíz cubre:

- la arquitectura y la regla de dependencias, con lo que cada crate **nunca** debe contener;
- los crates del runtime y de qué se encarga cada uno, para que el agente no copie su código;
- los comandos de `puerto`, la sintaxis de los campos, y qué ficheros se regeneran, cuáles se
  parchean y cuáles son tuyos;
- el orden de trabajo: generar, listar los escenarios, el test que falla, la regla en el dominio
  y después el endpoint, la API primero;
- las secciones de lo que el proyecto tiene activado: el frontend, los eventos de dominio, la
  auth, el correo;
- las convenciones: TDD, nombres de tests, códigos de error, logs, ningún `unwrap()`;
- las comprobaciones antes de decir «hecho»: `puerto validar`, `make test`, `make lint`,
  `make format`;
- cómo trabajar: un commit por pieza, y qué cambios tiene que leer una persona.

`contextos/AGENTS.md` recorre un contexto fichero a fichero, con las reglas que un agente tiene
más probabilidades de romper: los dos constructores, los ids tipados, un fichero por caso de uso,
las escrituras por la unidad de trabajo en un proyecto con eventos, los tests junto al código, las
madres. `presentacion/AGENTS.md` dice qué está generado y no se edita, el contrato de errores, las
sondas de salud y la forma de un handler.

<Aside type="note" title="Con tests, para que no se desfasen">
Las instrucciones para agentes son salida generada, y Puerto las prueba como cualquier otra: el
fichero raíz tiene que cubrir lo esencial, y ningún `AGENTS.md` puede describir algo que el
generador ya no hace, como un fichero `mod.rs` o el antiguo puerto de logger. Antes de que
existiera ese test se habían desfasado, y los agentes seguían reglas equivocadas
([ADR-0010](/docs/decisions/adr/0010-generated-agent-rules-are-tested/)).
</Aside>

## El compilador hace la revisión

Un agente que ha usado repositorios en otros frameworks buscará `guardar`. En un proyecto Puerto
con eventos de dominio, el repositorio no lo tiene, así que es un error de compilación:

Esa salida no está escrita a mano: un script genera un proyecto, escribe ese caso de uso y ejecuta
`cargo check`, tras cada release de Puerto. El agente la lee, encuentra el `uow_factory` junto al
repositorio en el mismo struct, pasa a la unidad de trabajo, y el evento queda registrado. Nadie
tuvo que verlo en la revisión. Lo mismo pasa al confundir los ids de dos entidades, con una
variante de error sin estado HTTP, con un consumidor que escucha un evento que ya no existe o con
un tipo del frontend que no coincide con la API.

## Generadores en vez de cableado

El código que un agente tiene más probabilidades de escribir mal sin que se note es el que conecta
cosas: la inyección de dependencias, las declaraciones de módulos, las tablas de rutas, la raíz de
composición del frontend. En un proyecto Puerto el agente no lo escribe. `AGENTS.md` le dice que
ejecute el generador:

```bash
puerto generar scaffold Producto -- nombre:String precio:i64 sku:String!
puerto generar caso-de-uso Producto cambiar_precio_producto
puerto generar bootstrap
puerto validar
```

Para funcionalidades más grandes, los [generadores capa a capa](/docs/guides/layer-by-layer/)
mantienen el contexto del agente en un crate cada vez: primero el dominio, con tests, y después el
siguiente.

## Dónde sigue leyendo el diff una persona

El `AGENTS.md` generado ordena los cambios según lo que perdona el sistema cuando están mal (llama
a los niveles `Nivel 1` y `Nivel 2`):

- **Nivel 1: falla en silencio, despacio o caro.** Que los tests estén en verde no basta; una
  persona lee el diff entero antes del commit. Migraciones SQL, dinero y cualquier aritmética de la
  que dependa el negocio, autenticación y autorización, unicidad y deduplicación, datos que cruzan
  la frontera de un cliente o de un tenant.
- **Nivel 2: falla con ruido y se puede deshacer.** Basta con las comprobaciones. Traducciones
  entre DTO y dominio, adaptadores con tests de integración reales, consultas de solo lectura,
  documentación.

Un cambio que toca los dos es de Nivel 1. Y el agente hace **un commit por pieza**, en verde, así
que el historial muestra lo que hizo en pasos que una persona puede revisar.

## Las actualizaciones también son prompts

Cuando una release cambia el código generado, su guía de migración en el
[changelog](/docs/changelog/) incluye un párrafo escrito para dárselo tal cual a un agente. Mira
[Actualizar](/docs/guides/upgrading/).
