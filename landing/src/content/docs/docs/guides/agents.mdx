Puerto is built on one bet: **the stricter the structure, the better an agent works inside it.**
An agent writing into a codebase where every project looks different has to guess, and its
guesses look plausible. An agent writing into a Puerto project has rules it can read, generators
that write the wiring, and a compiler that refuses architectural mistakes with a precise message.

## The rules ship with the project

Every project has a root `AGENTS.md` and a one-line `CLAUDE.md` (`@AGENTS.md`), so Claude Code,
Codex, Cursor and the rest load the same instructions. Each crate (`business/`,
`infrastructure/`, `presentation/`, `web/`, `worker/`) has its own `AGENTS.md` with the detail of
that layer.

The root file covers:

- the architecture and the dependency rule, with what each crate must **never** contain;
- the runtime crates and what each one owns, so the agent does not copy their code in;
- the `puerto` commands, and which files are regenerated and must not be edited;
- the sections for what the project has turned on: the frontend, domain events, auth, mail;
- the conventions: TDD, test names, error codes, logging, no `unwrap()`;
- the checks to run before saying "done": `make test`, `make lint`, `make format`;
- how to work: one commit per piece, and which changes a human must read.

<Aside type="note" title="Tested, so it cannot drift">
Agent instructions are generated output, and Puerto tests them like any other: the root file must
cover the essentials, and no `AGENTS.md` may describe something the generator no longer does, such
as a `mod.rs` file or the old logger port. Before that test existed they had drifted, and agents
followed the wrong rules ([ADR-0010](/docs/decisions/adr/0010-generated-agent-rules-are-tested/)).
</Aside>

## The compiler does the reviewing

An agent that has used repositories in other frameworks will reach for `save`. In a Puerto
project with domain events, that is a compile error, and `rustc` points at the right port:

That output is not written by hand: a script generates a project, writes that use case and runs
`cargo check`, after every Puerto release. The agent reads it, switches to the unit of work, and the event gets recorded. Nobody
had to catch it in review. The same goes for mixing up two entities' ids, an error variant without
an HTTP status, a consumer listening to an event that no longer exists, or a frontend type that
disagrees with the API. [The architecture](/docs/start/architecture/#what-the-compiler-enforces-for-you)
lists them.

## Generators instead of wiring

The code an agent is most likely to get subtly wrong is the code that connects things:
dependency injection, module declarations, route tables, the frontend's composition root. In a
Puerto project the agent does not write it. `AGENTS.md` tells it to run the generator:

```bash
puerto generate scaffold <Name> -- title:String price:i64!
puerto generate use-case <Entity> <action>
puerto generate bootstrap
puerto validate
```

For bigger features, the [layer-by-layer generators](/docs/guides/layer-by-layer/) keep the
agent's context to one layer at a time: domain first, tested, then the next.

## Where a person still reads the diff

The generated `AGENTS.md` sorts changes by how forgiving the system is when they are wrong:

- **Tier 1: fails silently, slowly or expensively.** A green suite is not enough; a person reads
  the whole diff before it is committed. SQL migrations, money and other arithmetic the business
  relies on, authentication and authorization, uniqueness and deduplication, data that crosses a
  tenant or customer boundary.
- **Tier 2: fails loudly and reversibly.** The checks are enough. DTO and domain mapping,
  adapters with real integration tests, read-only queries, docs.

A change that touches both is Tier 1. And the agent makes **one commit per piece**, green, so the
history shows what it did in steps a person can review.

## Upgrades are prompts too

When a release changes generated code, its migration guide in the [changelog](/docs/changelog/)
includes a paragraph written to be handed to a coding agent as is. See
[Upgrading](/docs/guides/upgrading/).
