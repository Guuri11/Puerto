title: Eventos de dominio
description: Registra un evento con cada escritura mediante un outbox transaccional, reacciona a él en un proceso worker aparte y elige Postgres o Kafka como transporte.

import { Steps, Aside, Tabs, TabItem } from '@astrojs/starlight/components';

Tarde o temprano algo tiene que pasar *porque* pasó otra cosa: enviar un correo de bienvenida
cuando un cliente se registra, actualizar una proyección cuando se paga un pedido, avisar a otro
servicio. Si cada reacción es una llamada dentro del caso de uso, cada reacción nueva obliga a
editar un caso de uso que ya funciona, y un fallo a medias deja a la base de datos y al mundo en
desacuerdo.

Puerto lo resuelve con el **outbox transaccional**. Cada escritura registra un evento en la misma
transacción que los datos, y un segundo proceso lo entrega, al menos una vez, a quien se haya
suscrito. El caso de uso no sabe quién escucha.

```bash
puerto nuevo --nombre tienda --db --eventos db      # o --eventos kafka
```

Los eventos necesitan `--db`: la garantía sale de la transacción.
[ADR-0018](/docs/decisions/adr/0018-domain-events-outbox-pluggable-transport/) tiene el diseño
entero.

## Cómo fluye

```txt
proceso de la API
  crear_producto
    (producto, evento) = Producto::crear(props)      la entidad emite Creado
    uow_factory.guardar(&producto, evento)  ┐ begin, guardar, registrar, commit:
                                            ┘ la fila de productos + la fila del outbox

proceso worker
  relay         lee el outbox en orden y entrega cada evento al transporte
                  db:    una fila de entregas_eventos por consumidor suscrito
                  kafka: topic tienda.producto, con el id del producto como clave
  consumidores  manejar(evento) → Ack | Reintentar | Descartar
```

Si el proceso muere antes del `commit`, no existen ni el producto ni el evento. Si muere después,
existen los dos, y el worker entregará el evento cuando arranque.

## Las escrituras van por la unidad de trabajo

En un proyecto con eventos cada entidad recibe una unidad de trabajo, y **su repositorio pierde
`guardar`**:

```rust title="contextos/producto/dominio/src/repositorio.rs"
pub trait RepositorioProducto: Send + Sync {
    async fn buscar_todos(
        &self,
        pagina: PeticionPagina,
    ) -> Result<Pagina<Producto>, ErrorRepositorio>;
    async fn buscar_por_id(&self, id: IdProducto) -> Result<Option<Producto>, ErrorRepositorio>;
    // Sin `guardar`: las escrituras pasan por `UnitOfWorkFactoryProducto`, que registra sus
    // eventos.
}
```

Así que una escritura que se salta el outbox no es un bug que encuentras en producción. No
compila:

```txt
error[E0599]: no method named `guardar` found for struct `Arc<(dyn RepositorioProducto + 'static)>` in the current scope
```

El evento lo decide la entidad: `Producto::crear(props)` devuelve el producto y su `Creado`, y
`actualizar` y `borrar` devuelven su evento. Los casos de uso generados de crear, actualizar y
borrar lo guardan con la entidad en una llamada:

```rust title="contextos/producto/aplicacion/src/crear_producto.rs (fragmento)"
let (entidad, evento) = Producto::crear(PropsProducto { nombre, precio, sku })?;
self.uow_factory.guardar(&entidad, evento).await?;
```

`guardar` abre la unidad de trabajo, guarda, registra el evento y confirma. `EventoProducto` es
`#[must_use]`: un evento emitido que nadie guarda es un aviso, y `make lint` lo rechaza.

Para escribir más de una vez en una transacción, los pasos a mano: `begin()`, `guardar`,
`registrar`, `commit()`. Soltar la unidad de trabajo sin `commit` lo deshace todo, así que un `?`
temprano es el rollback. Un agregado por transacción: un caso de uso que tiene que escribir dos de
forma atómica se escribe a mano contra un puerto propio. El porqué, en la
[ADR-0026](/docs/decisions/adr/0026-casos-de-uso-sin-fontaneria/).

## El evento es un contrato, no el modelo

`contextos/producto/dominio/src/eventos.rs` se regenera desde `puerto.toml`. Tiene el enum de
eventos y un **snapshot**: la entidad tal como la muestra la API, solo primitivos, con los objetos
valor deshechos.

```rust title="contextos/producto/dominio/src/eventos.rs (fragmento)"
pub const PRODUCTO_CREADO: &str = "producto_creado";

#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct SnapshotProducto {
    pub id: Uuid,
    pub nombre: String,
    pub precio: i64,
    pub sku: String,
}

pub enum EventoProducto {
    Creado(SnapshotProducto),
    Actualizado(SnapshotProducto),
    Borrado(SnapshotProducto),
}
```

El modelo de dominio nunca toca serde. Los consumidores decodifican el snapshot, así que
renombrar un campo cambia un contrato público, y se ve en `eventos.rs`, donde se puede revisar.

## Tus propios eventos

```bash
puerto generar evento Producto producto_publicado
```

```txt title="salida"
✓ Evento 'producto_publicado' añadido a Producto: EventoProducto::Publicado
  contextos/producto/dominio/src/eventos.rs regenerado.
  Emítelo desde un método de Producto que devuelva EventoProducto::Publicado(SnapshotProducto::from_entidad(self)), y guárdalo con self.uow_factory.guardar(&entidad, evento)
```

Los tipos de evento van en snake_case y en participio: algo que ya pasó.

El evento lo emite un método de la entidad que escribes tú: la regla de negocio y el hecho que
provoca van juntos, en el dominio.

```rust title="contextos/producto/dominio/src/modelo.rs (fragmento)"
impl Producto {
    pub fn publicar(&mut self) -> Result<EventoProducto, ErrorProducto> {
        if self.precio <= 0 {
            return Err(ErrorProducto::Validacion("precio_no_positivo".into()));
        }
        self.actualizado_en = chrono::Utc::now();
        Ok(EventoProducto::Publicado(SnapshotProducto::from_entidad(self)))
    }
}
```

`puerto generar caso-de-uso Producto publicar_producto` le da a `PublicarProductoImpl` el
repositorio, para leer, y la factoría de unidades de trabajo, para escribir. El cuerpo lee el
producto, le pide el evento y lo guarda con él:

```rust title="contextos/producto/aplicacion/src/publicar_producto.rs (fragmento)"
pub struct ParamsPublicarProducto {
    pub id: IdProducto,
}

#[async_trait]
impl PublicarProducto for PublicarProductoImpl {
    #[tracing::instrument(name = "publicar_producto", skip_all, fields(id = %params.id), err(level = "warn"))]
    async fn ejecutar(&self, params: ParamsPublicarProducto) -> Result<Producto, ErrorProducto> {
        let mut entidad = self
            .repositorio
            .buscar_por_id(params.id)
            .await?
            .ok_or(ErrorProducto::NoEncontrado)?;
        let evento = entidad.publicar()?;
        self.uow_factory.guardar(&entidad, evento).await?;
        Ok(entidad)
    }
}
```

Sus tests no necesitan base de datos. `UnitOfWorkFactoryGrabadora`, junto al puerto en
`dominio_producto::unit_of_work::dobles`, graba lo que cada unidad de trabajo guardó y registró, y
si confirmó:

```rust title="contextos/producto/aplicacion/src/publicar_producto.rs (fragmento)"
#[cfg(test)]
mod tests {
    use super::*;
    use dominio_producto::pruebas::madres::MadreProducto;
    use dominio_producto::repositorio::dobles::MockRepositorioProducto;
    use dominio_producto::unit_of_work::dobles::UnitOfWorkFactoryGrabadora;
    use puerto_nucleo::EventoDominio;

    fn caso_de_uso_con(
        producto: Producto,
        uow_factory: &UnitOfWorkFactoryGrabadora,
    ) -> PublicarProductoImpl {
        let mut repositorio_doble = MockRepositorioProducto::new();
        repositorio_doble
            .expect_buscar_por_id()
            .returning(move |_| Ok(Some(producto.clone())));
        PublicarProductoImpl {
            repositorio: Arc::new(repositorio_doble),
            uow_factory: Arc::new(uow_factory.clone()),
        }
    }

    #[tokio::test]
    async fn deberia_registrar_producto_publicado_cuando_el_producto_tiene_precio() {
        // Preparar
        let producto = MadreProducto::new().con_precio(1999).construir();
        let uow_factory = UnitOfWorkFactoryGrabadora::new();
        let caso_de_uso = caso_de_uso_con(producto.clone(), &uow_factory);

        // Actuar
        let resultado = caso_de_uso
            .ejecutar(ParamsPublicarProducto { id: producto.id })
            .await;

        // Comprobar
        assert!(resultado.is_ok());
        let grabado = uow_factory.grabado();
        assert!(grabado.confirmado);
        assert_eq!(grabado.eventos.len(), 1);
        assert_eq!(grabado.eventos[0].tipo_evento(), "producto_publicado");
    }
}
```

Para los caminos de error, `UnitOfWorkFactoryGrabadora::fallando_en(FallarEn::Guardar,
ErrorRepositorio::Duplicado)` falla en el paso que nombres; una escritura rechazada deja
`grabado().eventos` vacío y `confirmado` en false.

## Consumidores

<Steps>

1. **Genera uno.**

   ```bash
   puerto generar consumidor avisar_producto_nuevo --tras producto_creado,producto_publicado
   ```

   ```txt title="salida"
   ✓ Consumidor 'avisar_producto_nuevo' añadido, tras: producto_creado, producto_publicado
     presentacion/worker/src/consumidores/avisar_producto_nuevo.rs es tuyo: hazlo idempotente, puede recibir un evento dos veces.
     presentacion/worker/src/generado/registro.rs regenerado. Arráncalo con `make worker`.
   ```

2. **Escribe lo que hace.** El esqueleto es un `ManejadorEvento` que decodifica el snapshot y
   confirma:

   ```rust title="presentacion/worker/src/consumidores/avisar_producto_nuevo.rs (fragmento)"
   #[async_trait]
   impl ManejadorEvento for AvisarProductoNuevo {
       async fn manejar(&self, evento: &SobreEvento) -> ResultadoManejo {
           match evento.tipo_evento.as_str() {
               PRODUCTO_CREADO => match evento.decodificar::<SnapshotProducto>() {
                   Ok(producto) => {
                       tracing::info!(
                           id_evento = %evento.id,
                           id_producto = %producto.id,
                           "avisar_producto_nuevo: producto_creado"
                       );
                       ResultadoManejo::Ack
                   }
                   Err(err) => ResultadoManejo::descartar(MOTIVO_PAYLOAD_INVALIDO, err.detalle),
               },
               // …
               _ => ResultadoManejo::Ack,
           }
       }
   }
   ```

   Responde `ResultadoManejo::Ack` al terminar, `Reintentar` ante un fallo que puede pasar (un
   timeout, un servicio caído) y `ResultadoManejo::descartar(…)` ante uno que no pasará nunca.

3. **Dale lo que necesita.** El worker construye cada consumidor una vez, con su pool de base de
   datos, mediante el `construir` del propio fichero del consumidor. Guarda lo que necesita en los
   campos del struct:

   ```rust title="presentacion/worker/src/consumidores/actualizar_clasificacion.rs (fragmento)"
   pub struct ActualizarClasificacion {
       recalcular: Arc<dyn RecalcularClasificacion>,
   }

   impl ActualizarClasificacion {
       pub fn construir(pool: &PgPool) -> Self {
           Self {
               recalcular: cableado::clasificacion::construir(pool).recalcular_clasificacion,
           }
       }
   }
   ```

   `cableado::<contexto>::construir(pool)` da los casos de uso de un contexto, los mismos que
   sirve la API. Añade `cableado = { workspace = true }` a `presentacion/worker/Cargo.toml` la
   primera vez; el esqueleto no depende de él, así que un proyecto sin un consumidor así no recibe
   el aviso de dependencia sin usar. Los tests construyen el struct con el doble del caso de uso.

4. **Hazlo idempotente.** La entrega es **al menos una vez**: tras una caída o un despliegue, el
   mismo evento puede llegar dos veces, con el mismo `evento.id`. Comprueba si el trabajo ya se
   hizo, con `evento.id` como clave, antes de volver a hacerlo. Por eso los tests generados
   entregan el mismo sobre dos veces.

5. **Arranca el worker.**

   ```bash
   make worker      # saca los eventos del outbox y ejecuta los consumidores; salud en :8081
   ```

</Steps>

`presentacion/worker/src/generado/registro.rs` cablea el relay y un bucle por consumidor desde los
bloques `[[consumidor]]` de `puerto.toml`; se regenera, nunca se edita. Los tipos de evento son
constantes generadas, así que quitar un evento que escucha un consumidor rompe la compilación del
worker en lugar de dejar al consumidor sin eventos en silencio.

## Reintentos y descartados

Todos los transportes aplican la misma política de entrega, de `puerto-nucleo`:

| Entrega fallida | 1.ª | 2.ª | 3.ª | 4.ª | 5.ª |
|---|---|---|---|---|---|
| Después | espera 1 s | espera 5 s | espera 15 s | espera 60 s | descartado |

Un `Reintentar` en la última entrega permitida (`MAX_DELIVERIES`, 5 por defecto) retira el evento
con una fila en `descartados`; sube el tope y las esperas siguen en 300 s. Nada se retira sin una
fila en descartados, y si escribirla falla, el evento se vuelve a entregar. Un manejador que hace
panic cuenta como un `Reintentar`.

```bash
make eventos/descartados     # los 20 más recientes: consumidor, tipo de evento, intentos, motivo
```

## Transportes

<Tabs>
<TabItem label="db">
Sin broker. El relay inserta una fila de `entregas_eventos` por consumidor suscrito en la misma
transacción que marca como publicada la fila del outbox, y cada consumidor reclama sus filas con
`FOR UPDATE SKIP LOCKED`. El orden por agregado se mantiene con una réplica del worker por
consumidor. Un consumidor añadido más tarde recibe los eventos que salen después de desplegarlo.
</TabItem>
<TabItem label="kafka">
El relay publica en el topic `<proyecto>.<agregado>` (`tienda.producto`), con el id del agregado
como clave y los campos del sobre como cabeceras. Cada consumidor es un grupo de consumidores
llamado `<proyecto>.<consumidor>`, y los offsets se confirman tras el resultado. Un reintento se
retiene en el proceso, lo que para la suscripción y mantiene el orden. El outbox y los descartados
se quedan en Postgres.

El transporte es el crate `puerto-kafka`. `ConfigKafka::from_env` lee `KAFKA_BROKERS` y
`KAFKA_TOPIC_PREFIX` (por defecto, el nombre del proyecto), y el worker llama a
`asegurar_topics(&["producto"])` al arrancar, así que los topics existen antes de que el relay
publique. `docker-compose.yml` arranca Redpanda para desarrollo, y compilar pide `cmake` y las
cabeceras de libcurl.
</TabItem>
</Tabs>

## Varios workers

El relay toma un advisory lock de Postgres, así que con varias réplicas solo una saca los eventos
y el orden del outbox se mantiene. Los consumidores escalan con las réplicas. Cada worker sirve
`/health` y `/health/ready` en `WORKER_PORT`: está listo mientras cada bucle haya terminado una
pasada sin fallar dentro de su intervalo, así que una base de datos caída se ve como no listo.

| Variable | Por defecto | |
|---|---|---|
| `WORKER_PORT` | `8081` | sondas de salud |
| `RELAY_BATCH_SIZE` | `100` | filas del outbox por pasada del relay |
| `RELAY_POLL_INTERVAL_MS` | `500` | espera del relay cuando no hay nada |
| `CONSUMER_POLL_INTERVAL_MS` | `500` | espera de un consumidor cuando no hay nada |
| `MAX_DELIVERIES` | `5` | intentos antes de descartar |
| `RETRY_MAX_DELAY_MS` | la de la política | acota la espera (los tests usan `0`) |
