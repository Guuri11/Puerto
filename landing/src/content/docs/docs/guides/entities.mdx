Una entidad es algo que le importa a tu negocio y tiene identidad a lo largo del tiempo: un
`Producto`, un `Pedido`, un `Cliente`. En Puerto, una entidad es además la unidad de generación.
Un comando la escribe en todas las capas.

```bash
puerto generar scaffold Pedido -- importe:Importe:f64 estado:Estado:enum:Pendiente/Confirmado/Cancelado nota:opt:String
```

El nombre va en PascalCase; Puerto deriva `pedido` para el contexto, los crates y los módulos,
`pedidos` para la tabla y las rutas, e `IdPedido` para el id. Los campos van tras `--`. La
[referencia de tipos de campo](/docs/reference/field-types/) lista todos los tipos y en qué se
convierten en cada capa.

## Lo que escribe

Cada entidad es un contexto, `contextos/pedido/`, con un crate por capa: `dominio_pedido`,
`aplicacion_pedido`, `infra_pedido` y `rest_pedido` (la API HTTP), así que la regla de
dependencias la impone Cargo ([ADR-0023](/docs/decisions/adr/0023-crates-por-contexto-y-capa/)).

<FileTree>

Cada crate tiene su `Cargo.toml` y un `lib.rs` plano. El scaffold también añade los crates al
`Cargo.toml` raíz y a `presentacion/api/Cargo.toml`, añade la entidad a `puerto.toml`, regenera
`presentacion/cableado/` y `presentacion/api/src/generado/bootstrap.rs` y, en un proyecto con web,
la tabla de rutas del frontend. Después ejecuta `cargo fmt`.

## Los cinco endpoints

| Caso de uso | Ruta | Éxito |
|---|---|---|
| `crear_pedido` | `POST /api/pedidos` | `201` + el pedido |
| `obtener_pedido` | `GET /api/pedidos/:id` | `200` + el pedido |
| `listar_pedidos` | `GET /api/pedidos?limite=&desplazamiento=` | `200` + una página |
| `actualizar_pedido` | `PUT /api/pedidos/:id` | `200` + el pedido |
| `borrar_pedido` | `DELETE /api/pedidos/:id` | `204` |

Las listas son páginas, `{ elementos, total, limite, desplazamiento }`: 20 elementos por defecto,
nunca más de 100. El tope es una regla del dominio (`PeticionPagina`), así que ninguna ruta ni
adaptador puede pedir más ([ADR-0016](/docs/decisions/adr/0016-lists-are-offset-pages/)). El
borrado es lógico.

## Las reglas van en el modelo

`Producto::new` crea uno y `Producto::actualizar` lo cambia. Los dos ejecutan `validar`, así que
una regla se escribe una vez y vale al crear y al actualizar:

```rust title="contextos/producto/dominio/src/modelo.rs"
impl Producto {
    pub fn new(props: PropsProducto) -> Result<Self, ErrorProducto> {
        Self::validar(&props)?;
        let ahora = chrono::Utc::now();
        Ok(Self {
            id: IdProducto::generar(),
            // …
        })
    }

    /// Cambia los campos propios, con las mismas reglas que `new`.
    pub fn actualizar(&mut self, props: PropsProducto) -> Result<(), ErrorProducto> {
        Self::validar(&props)?;
        // …
    }

    fn validar(props: &PropsProducto) -> Result<(), ErrorProducto> {
        if props.nombre.trim().is_empty() {
            return Err(ErrorProducto::Validacion("nombre_vacio".into()));
        }
        // …
        Ok(())
    }
}
```

Los campos `String` obligatorios ya rechazan un valor vacío. Añade tus comprobaciones a
`validar`: devuelve una `Validacion` con un código en snake_case, y la API responde `422` con
`producto.validacion.<codigo>`. El formulario web lo muestra junto al campo cuando el código nombra
uno. Si una regla nueva rechaza uno de los valores por defecto de la madre, cambia el valor en la
madre: los tests generados sacan sus valores de ella (mira [Tests](/docs/guides/testing/#las-madres)).

## Únicos sobre varios campos, y el orden de la lista

Un campo que termina en `!` es único por sí solo. Un único sobre varios campos, y el orden de la
lista, son flags del scaffold:

```bash
puerto generar scaffold Linea \
  --unico jugador_id,partido_id \
  --orden=-puntos,jugador_id \
  -- jugador_id:ref:Jugador partido_id:ref:Partido puntos:i64
```

`--unico` (se puede repetir) es un índice único parcial por grupo en Postgres,
`lineas_jugador_id_partido_id_key … WHERE borrado = false`, y también un `Duplicado` del
repositorio en memoria: una segunda fila con el mismo jugador y el mismo partido responde `409`.
`--orden` lista por esos campos (`-` para descendente) y después lo más nuevo primero:
`ORDER BY puntos DESC, jugador_id, creado_en DESC, id`. Los dos quedan en el bloque `[[entidad]]`
(`unicos`, `orden`), y un re-scaffold sin el flag conserva lo que dice el bloque.

## Cada entidad tiene su propio tipo de id

```rust
pub struct IdProducto(Uuid);
```

`IdProducto::generar()` crea uno nuevo, `IdProducto::from_uuid(u)` envuelve uno leído de una ruta
o de una fila, y `.valor()` lo deshace en los bordes. Un `IdCliente` no se puede pasar donde va un
`IdProducto`. El newtype se queda en el borde: las rutas reciben `Path<Uuid>`, y los DTO y las
filas guardan un `Uuid`, así que el contrato OpenAPI sigue siendo `string(uuid)`
([ADR-0014](/docs/decisions/adr/0014-entity-ids-are-generated-newtypes/)).

## Referenciar otra entidad

Una entidad que pertenece a otra guarda su id:

```bash
puerto generar scaffold Cliente -- nombre:String email:String!
puerto generar scaffold Pedido -- cliente_id:ref:Cliente revisor_id:ref:opt:Cliente total:i64
```

`Pedido.cliente_id` es un `IdCliente`, no un `Cliente`: no hay navegación ni carga perezosa, y un
caso de uso que necesita el cliente se lo pide a su repositorio. La referencia es además una
dependencia entre crates: `dominio_pedido` depende de `dominio_cliente`, dueño de `IdCliente`, así
que Cargo rechaza un ciclo. En un proyecto `--db` la columna tiene una clave foránea, así que un
pedido de un cliente que no existe lo rechaza Postgres y se responde `422` con
`pedido.validacion.cliente_id_no_encontrado`. `GET /pedidos?clienteId=` lista los pedidos de un
cliente, y el formulario web elige el cliente en un `<select>`
([ADR-0022](/docs/decisions/adr/0022-references-are-typed-ids-checked-by-foreign-keys/)). El
objetivo tiene que estar generado antes. Mira [Referencias](/docs/reference/field-types/#referencias).

## Tras el scaffold, los ficheros son tuyos

Todo salvo los ficheros regenerados se escribe una vez y desde entonces es tuyo. Cambia el
modelo, añade métodos, reescribe un caso de uso. Volver a ejecutar `scaffold` para la misma
entidad se rechaza:

```txt
'producto' ya está generada: esto sobrescribiría 30 fichero(s):
  contextos/producto/dominio/src/modelo.rs
  contextos/producto/dominio/src/errores.rs
  contextos/producto/dominio/src/repositorio.rs
  contextos/producto/dominio/src/pruebas/madres.rs
  contextos/producto/aplicacion/src/crear_producto.rs
  contextos/producto/aplicacion/src/obtener_producto.rs
  contextos/producto/aplicacion/src/listar_productos.rs
  contextos/producto/aplicacion/src/actualizar_producto.rs
  contextos/producto/aplicacion/src/borrar_producto.rs
  contextos/producto/infraestructura/src/repositorio.rs
  … y 20 más

Error: no se sobrescriben los ficheros de 'producto'. Vuelve a ejecutarlo con --forzar para sobrescribirlos, o borra antes los ficheros. No se ha escrito nada.
```

`--forzar` regenera la entidad y **descarta tus cambios** en sus ficheros. Existe para el momento
justo después de un scaffold, cuando te has equivocado en un campo.

<Aside type="tip">
Para añadir un campo más tarde, añádelo al `[[entidad.campos]]` de la entidad en `puerto.toml`, y
actualiza a mano el modelo, el DTO, la fila y una migración nueva, o usa `--forzar` en el scaffold
si aún no has cambiado nada. Los [snippets del IDE](/docs/guides/configuration/#snippets-del-ide)
cubren las formas habituales.
</Aside>

## Una capa cada vez

`scaffold` es un atajo de cuatro comandos, un crate cada uno. Cuando quieras diseñar primero el
dominio, o mantener pequeño el contexto de un agente, ejecútalos uno a uno. Mira
[Capa a capa](/docs/guides/layer-by-layer/).
