Un objeto valor es un valor con un significado y una regla: un `Email` es una cadena, pero no
cualquier cadena es un email. Darle su propio tipo hace que la regla se compruebe una vez, al
construir el valor, y que nada más adelante pueda pasarle una cadena suelta a un código que espera
un email.

## Declararlo en un campo

La segunda parte del campo es el nombre del objeto valor:

```bash
puerto generar scaffold Pedido -- importe:Importe:f64 estado:Estado:enum:Pendiente/Confirmado/Cancelado
```

```rust title="contextos/pedido/dominio/src/valores.rs"
#[derive(Debug, Clone, Copy, PartialEq)]
pub struct Importe(f64);

impl Importe {
    pub fn new(valor: f64) -> Result<Self, ErrorPedido> {
        Ok(Self(valor))
    }

    pub fn valor(&self) -> f64 {
        self.0
    }
}
```

`new` es donde va la regla, y empieza vacío porque solo tú la conoces:

```rust
pub fn new(valor: f64) -> Result<Self, ErrorPedido> {
    if valor <= 0.0 {
        return Err(ErrorPedido::ImporteInvalido);
    }
    Ok(Self(valor))
}
```

`ErrorPedido::ImporteInvalido` ya está generado, con su `422`. La API responde
`pedido.importe_invalido`, y el formulario web muestra «Importe: no válido» bajo el campo.

## Enums

`estado:Estado:enum:Pendiente/Confirmado/Cancelado` genera un `enum` de Rust con `FromStr` y
`as_str()`:

```rust
let estado: Estado = "Confirmado".parse()?;   // Err(ErrorPedido::EstadoInvalido) con cualquier otro
estado.as_str();                                // "Confirmado"
```

Implementa `FromStr` y no un `from_str` propio, así que clippy no se queja y `.parse()` no necesita
import ([ADR-0001](/docs/decisions/adr/0001-enum-value-objects-implement-fromstr/)). En el JSON es
una cadena, y el formulario web ofrece sus variantes en un `<select>`.

## Email y dinero: las clases con regla

Dos formas son tan comunes que Puerto ya trae su regla. Van donde va `enum`, y el tipo sale de la
clase:

```bash
puerto generar scaffold Concierto -- titulo:String precio:Precio:dinero contacto:Contacto:email
```

`dinero` es un `i64` de céntimos que nunca es negativo; `email`, un `String` recortado con la forma
`usuario@dominio.tld`:

```rust title="contextos/concierto/dominio/src/valores.rs"
impl Precio {
    pub fn new(valor: i64) -> Result<Self, ErrorConcierto> {
        if valor < 0 {
            return Err(ErrorConcierto::PrecioInvalido);
        }
        Ok(Self(valor))
    }
}
```

La forma, no que el buzón exista. `valores.rs` lleva un test por regla. En la web, un `email` es un
`<input type="email">`, y el dinero se escribe en euros con coma («12,50») y se muestra con
`euros()` («12,50 €»): el formulario lo convierte con `aImporte` y `deImporte`, en
`compartido/formularios.ts`. La API sigue hablando en céntimos.

## Opcionales y repetidos

```bash
puerto generar scaffold Cliente -- apodo:Apodo:opt:String etiquetas:Etiqueta:vec:String
```

`apodo` es un `Option<Apodo>` y `etiquetas` un `Vec<Etiqueta>`. Cada elemento lo valida el mismo
`new`.

## Objetos valor compartidos

Cuando varias entidades usan el mismo concepto, se declara una vez:

```bash
puerto generar objeto-valor Email String
puerto generar scaffold Cliente -- email:Email! nombre:String
puerto generar scaffold Proveedor -- email:Email nombre:String
```

El tipo sale de la declaración, así que basta con `email:Email`. Los objetos valor compartidos
viven en el crate `nucleo` (`nucleo/src/valores.rs`), con su propio error en
`nucleo/src/errores.rs`, y `puerto.toml` los registra:

```toml
[[objeto_valor]]
nombre = "Email"
tipo = "String"
```

Un objeto valor compartido empieza con una regla de verdad, un valor recortado y no vacío, que
puedes endurecer en un solo sitio para todas las entidades:

```rust title="nucleo/src/valores.rs"
impl Email {
    pub fn new(valor: String) -> Result<Self, ErrorEmail> {
        let recortado = valor.trim().to_string();
        if recortado.is_empty() {
            return Err(ErrorEmail::Invalido);
        }
        Ok(Self { valor: recortado })
    }
}
```

Cada entidad lo sigue contando en sus términos: un email inválido en un cliente es
`cliente.email_invalido`, y en un proveedor `proveedor.email_invalido`.

Un compartido también puede tener clase, `puerto generar objeto-valor Email email`, y sus campos la
reciben (`[[objeto_valor]] clase = "email"`).

## El valor de los tests

Los tests generados construyen cada campo con un valor válido: `"example"` en un `String`, `42` en
un número. Cuando la regla de un compartido rechaza ese valor, rompería las madres de todas las
entidades que lo usan. Dale un ejemplo al declararlo:

```bash
puerto generar objeto-valor Email email --ejemplo hola@aforo.es
```

```rust title="contextos/sala/dominio/src/pruebas/madres.rs"
Email::new("hola@aforo.es".to_string())
```

Lo usan la madre, los cuerpos de los tests de rutas y de casos de uso, la siembra de los tests de
Postgres y la madre de la web. Vale en un `String` no vacío, un `i64`, un `f64` o un `bool`, y
`puerto validar` comprueba que se lee como su tipo. Sin `--ejemplo`, un `email` usa
`ana@ejemplo.es`. En un objeto valor local que endureces a mano, cambia el valor en su madre (mira
[Tests](/docs/guides/testing/#las-madres)).

## Hasta dónde llegan los objetos valor

Los objetos valor viven en el dominio. La infraestructura y el crate REST ven el primitivo: la
fila tiene una columna `String` y el DTO un campo `String`. La conversión se hace en el borde, en
código que genera Puerto: el caso de uso construye el objeto valor desde los params, y la fila y el
DTO lo deshacen con `.valor()`.

<Aside type="note">
Un objeto valor nunca llega a serde. Los snapshots de los eventos, que sí llegan, llevan el
primitivo ([ADR-0018](/docs/decisions/adr/0018-domain-events-outbox-pluggable-transport/) § 3),
así que el modelo de dominio puede cambiar sin cambiar un contrato público.
</Aside>
