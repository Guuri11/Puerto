Un proyecto Puerto tiene dos cosas que cambian con Puerto: el código que generó, que es tuyo, y
los crates del runtime de los que depende, que no lo son. Se actualizan de forma distinta.

## Los parches llegan con `cargo update`

Los crates del runtime (`puerto-nucleo`, `puerto-web`, `puerto-sqlx` y los demás) se publican a
la vez que la CLI, y un proyecto pide la minor que lo generó:

```toml title="Cargo.toml"
[workspace.dependencies]
puerto-nucleo = "0.23"
puerto-web = "0.23"
```

Un arreglo en una release patch (`0.23.1`) llega al proyecto con `cargo update`. No hay nada que
regenerar. Para eso existe el runtime
([ADR-0017](/docs/decisions/adr/0017-runtime-crates-next-to-the-generator/)).

## Una minor nueva es un paso deliberado

Mientras Puerto esté en `0.x`, una minor puede cambiar lo que escribe el generador y la API del
runtime. Cada uno de esos cambios está bajo **Breaking** en el [changelog](/docs/changelog/), con
una **Migration Guide** cuando hay proyectos que migrar.

<Steps>

1. **Actualiza la CLI.**

   ```bash
   cargo install puerto --locked --force
   ```

2. **Pregúntale al proyecto.**

   ```bash
   puerto validar
   ```

   Avisa de cada crate del runtime que está en otra minor que la CLI.

3. **Lee la guía de migración** de cada minor que cruces, y aplícala. Sube los crates en el
   `Cargo.toml` raíz, y después:

   ```bash
   puerto generar bootstrap     # regenera lo que es de Puerto
   make test && make lint && make format
   ```

</Steps>

## La 0.21 no tiene guía de migración

La 0.21 cambió la forma de todos los proyectos generados: un crate por contexto y capa bajo
`contextos/`, `nucleo/` y `presentacion/`
([ADR-0023](/docs/decisions/adr/0023-crates-por-contexto-y-capa/)), y todo lo generado,
`puerto.toml` y la CLI en castellano
([ADR-0024](/docs/decisions/adr/0024-lo-generado-en-castellano/)). Los crates del runtime
`puerto-core`, `puerto-events` y `puerto-mail` pasaron a ser `puerto-nucleo`, `puerto-eventos` y
`puerto-correo`. Salió sin guía de migración, porque no había proyectos generados que migrar. Un
proyecto generado por la 0.20 sigue funcionando con los crates de la 0.20, que siguen en
crates.io; para pasarlo a la 0.21, genera un proyecto nuevo con `puerto nuevo` y trae tu código.

## Las guías de migración se escriben también para agentes

Cuando una release cambia el código generado, su guía termina con un párrafo pensado para
pegárselo tal cual a tu agente. Por ejemplo, el de la 0.14 (en inglés, como el changelog de
entonces):

> Upgrade this Puerto project from 0.13 to 0.14. In the root `Cargo.toml` add
> `[workspace.dependencies]` with `puerto-core = "0.14"`, `puerto-web = "0.14"` and, if
> `infrastructure` uses sqlx, `puerto-sqlx = "0.14"`; […] then run `puerto generate bootstrap`,
> `puerto validate` and `make test`.

El agente hace la parte mecánica, y los tests le dicen cuándo ha terminado.

<Aside type="note" title="Por qué el runtime se versiona así">
Todo enum público y todo struct que puedas recibir de un crate del runtime es `#[non_exhaustive]`
desde el primer día, así que una variante o un campo nuevo no es un cambio incompatible. Loco
necesitó una 1.0 para aprenderlo; Puerto lo escribió en la
[ADR-0017](/docs/decisions/adr/0017-runtime-crates-next-to-the-generator/) antes de la primera
release.
</Aside>
