`puerto nuevo` incluye `web/` salvo que pases `--sin-web`: una app React 19 con daisyUI sobre
Tailwind, que corre con Bun. `scaffold` escribe las pantallas de cada entidad (lista, detalle y un
formulario para crear y editar), así que lo primero que generas ya funciona en un navegador.

```bash
make web/install     # una vez
make web/dev         # http://localhost:5173, con /api redirigido a :8080
```

El frontend es la capa de presentación y poco más
([ADR-0025](/docs/decisions/adr/0025-el-frontend-es-presentacion/)): los contenedores llaman a la
API con su cliente tipado, y las vistas pintan lo que reciben. No tiene modelo de dominio, ni
puertos, ni adaptadores propios; las reglas viven en el backend. Como el backend, está en
castellano (`ContenedorListaProducto`, `useCarga`, `desenvolver`), y sus pantallas usan frases
neutras (`Crear producto`, `¿Borrar producto?`), porque Puerto no puede saber el género de una
entidad.

## La marca, el marco y el panel

Un proyecto nuevo ya se ve como un producto. Su marca vive en tres ficheros que escribe
`puerto nuevo` y que no vuelve a tocar
([ADR-0027](/docs/decisions/adr/0027-la-marca-es-del-proyecto/)):

- `web/src/marca/marca.ts`: el nombre (el del proyecto), el eslogan y la ruta del logo.
- `web/src/marca/tema.css`: los colores y los radios de la marca, sobre los temas claro y oscuro de
  daisyUI. La app sigue el modo del sistema. Para otro tema, genera uno en el
  [generador de temas de daisyUI](https://daisyui.com/theme-generator/) y pega sus variables.
- `web/public/logo.svg`: el logo, que también es el icono de la pestaña.

El marco pone la marca y el menú en un lateral, con la sección actual marcada; en el móvil, el
lateral se abre desde un botón. La página de inicio es el **panel**: una tarjeta por entidad con
el total de su lista, que sale del `total` de una página de un elemento
(`GET /productos?limite=1`), sin endpoints nuevos.

Con auth, el login y el registro (o la vuelta del proveedor OIDC) van fuera del marco, en una
página de acceso con la marca a un lado y el formulario en una tarjeta. El menú de usuario muestra
un avatar con las iniciales y lleva al **perfil** (`/perfil`), que enseña lo que responde
`GET /me`: nombre, email y roles.

## El contrato es la especificación OpenAPI

Las rutas del backend son poem-openapi, así que la API se describe sola. Un test de
`bootstrap.rs` exporta la especificación a `docs/api/openapi.json`, y los tipos del frontend se
generan desde ella con `openapi-typescript`. Las pantallas los usan directamente:
`Esquemas["DtoProducto"]`, `Esquemas["PeticionCrearProducto"]`.

```bash
make web/sync    # tras un scaffold, y tras tocar una ruta o un DTO
```

Vuelve a exportar la especificación, regenera `web/src/api/esquema.d.ts` y formatea `web/`. Haz
commit de los dos. Hasta que lo ejecutes, `make test` falla, justo en la pantalla que ya no encaja
con la API. Ese fallo es la comprobación de deriva: el frontend no puede llevarle la contraria a la
API en silencio.

## Una carpeta por clase de cosa

<FileTree>
- web/src/
  - api/
    - cliente.ts crearClienteApi, ClienteApi, Esquemas (los DTO por nombre)
    - http.ts desenvolver, ErrorApi, TAMANO_PAGINA
    - esquema.d.ts **generado** por make web/sync
  - contextos/producto/
    - contenedores/ lista, detalle, formulario: llamadas y estado, con tests
    - vistas/ lista, detalle, formulario: solo props
    - mensajes.ts qué dice cada código de error, y en qué campo
  - marca/
    - marca.ts tuyo: nombre, eslogan y logo
    - tema.css tuyo: los colores de la marca sobre los temas de daisyUI
  - paginas/ panel, no-encontrada
  - compartido/ formularios.ts, use-carga.ts, ui/ (marco, alertas, paginación, errores de campo)
  - generado/ **generado**: la raíz de composición y la tabla de rutas
  - rutas.tsx tuyo: rutas propias
  - pruebas/ renderizarPantalla, la API falsa, MadreProducto
</FileTree>

Un contenedor recibe el cliente de `useDependencias()` y desenvuelve cada llamada con
`desenvolver`, que rechaza con un `ErrorApi` que lleva el `codigo` de la API:

```tsx title="web/src/contextos/producto/contenedores/detalle-producto.tsx (fragmento)"
const { api } = useDependencias();
const producto = useCarga(
  () => desenvolver(api.GET("/productos/{id}", { params: { path: { id } } })),
  [api, id],
);
```

`dependency-cruiser` mantiene la separación en `make web/lint`, junto al chequeo de tipos y
Biome: una vista no puede importar el cliente, `useDependencias` ni `useCarga`, y solo
`generado/dependencias.ts` y los tests construyen el cliente. Cuando llegue lógica de cliente de
verdad, una regla o una orquestación, escríbela a mano donde corresponda.

## Los campos se convierten en controles

| Campo | Tipo en la API | Control |
|---|---|---|
| `String`, `Uuid` | `string` | input de texto, `required` |
| `i64`, `f64` | `number` | input numérico (`step=any` para `f64`) |
| `bool` | `boolean` | checkbox |
| `DateTime` | `string` (ISO 8601) | `datetime-local` |
| `opt:T` | `T`, opcional; `null` cuando falta | como `T`, no obligatorio; un input vacío no se manda |
| `vec:T` | `T[]` | texto, separado por comas |
| `map` | `Record<string, string>` | textarea, una línea `clave=valor` por entrada |
| objeto valor enum | `string` | `<select>` con sus variantes |
| `ref:Cliente` | `string` | `<select>` con los 100 primeros clientes; en el detalle, un enlace con la etiqueta del cliente, que carga el contenedor |

## Los errores aparecen junto a su campo

El frontend no copia la validación del dominio: la autoridad es el servidor. Un `422` vuelve con
su `codigo`, y `mensajes.ts`, generado de la misma lista que `errores.rs`, lo convierte en una
frase y un campo:

```ts title="web/src/contextos/cliente/mensajes.ts (fragmento)"
"cliente.email_invalido": "Email: no válido",
"cliente.validacion.nombre_vacio": "Nombre: obligatorio",
```

`cliente.validacion.nombre_vacio` marca el input `nombre`. `cliente.duplicado` («Estos valores ya
están en uso») va a la alerta del formulario. Un código para el que nadie escribió un mensaje se
muestra tal cual.

## Rutas

`/productos`, `/productos/nuevo`, `/productos/:id` y `/productos/:id/editar`. La página de la lista
va en la URL (`?pagina=2`), así que recargar y volver atrás la conservan. Añade tus rutas en
`rutas.tsx`, nunca en `generado/`, que se reescribe.

## Tests

`bun test` con happy-dom y Testing Library. Cada contenedor se prueba contra `apiFalsa`, un único
falso en memoria de la API generada para todas las entidades: responde páginas, `404` con
`<entidad>.no_encontrado`, `201`, `200` y `204`, y el código de error que le pida un test
(`{ "POST /productos": "producto.duplicado" }`). Los tests hablan HTTP, así que ejercitan las
rutas y los parámetros reales. `make test` y `make lint` incluyen `web/` siempre que exista el
directorio.
