import { Tabs, TabItem, Aside } from '@astrojs/starlight/components';

La auth es una decisión en `puerto nuevo`, y el resto sale de ella.

```bash
puerto nuevo --nombre tienda --db --auth oidc     # Auth0, Keycloak o cualquier proveedor OpenID Connect
puerto nuevo --nombre tienda --db --auth local    # cuentas y sesiones en esta base de datos
```

Los dos modos comparten un puerto, `Autenticador`, y una entidad `Usuario` en su propio
contexto, `contextos/usuario/`, así que las rutas, los casos de uso y las pantallas son los mismos
en los dos casos. `GET /api/me` responde quién llama, tal como lo resolvió la API. Pasar de
cuentas locales a un proveedor no toca tu dominio
([ADR-0021](/docs/decisions/adr/0021-auth-one-authenticator-port-oidc-or-local/)).

<Tabs>
<TabItem label="oidc">
La API es un **resource server** de OAuth2: comprueba los access tokens JWT del proveedor (RS256 o
ES256, `iss`, `aud`, `exp`/`nbf`) contra su JWKS, que se guarda en caché y se vuelve a pedir como
mucho una vez por minuto cuando aparece un `kid` desconocido. Auth0 y Keycloak son configuración,
no adaptadores.

La primera petición de quien llama crea su fila de `Usuario` (aprovisionamiento al vuelo, con una
caché de 60 segundos, en `contextos/usuario/infraestructura/src/aprovisionamiento.rs`). **Los
roles salen solo del token**, del claim que nombra `AUTH_ROLES_CLAIM`.

```ini title=".env"
AUTH_ISSUER=http://localhost:8180/realms/tienda
AUTH_AUDIENCE=api
AUTH_ROLES_CLAIM=realm_access.roles
```

Para Auth0: `AUTH_ISSUER=https://<tenant>.auth0.com/`, `AUTH_AUDIENCE` con el identificador de la
API, y `AUTH_ROLES_CLAIM` con `permissions` o con el claim que añada una Action.

En desarrollo, `docker-compose.yml` arranca Keycloak con un realm propio: un cliente público
`web` con PKCE, `admin@tienda.localhost` con el rol `admin`, y `user@tienda.localhost` sin él.

```bash
make auth/ui                                         # dónde está la consola de Keycloak, y cómo entrar
make -s auth/token EMAIL=user@tienda.localhost       # un access token, para curl
```

`--auth oidc` también funciona sin `--db`; entonces los usuarios se guardan en memoria.
</TabItem>
<TabItem label="local">
La API **es** el proveedor de identidad. Necesita `--db`.

| Ruta | Qué hace |
|---|---|
| `POST /api/auth/registro` | crea una cuenta con `email`, `contrasena` (12 caracteres como mínimo) y un `nombre` opcional; `201` con el usuario |
| `POST /api/auth/login` | recibe `email` y `contrasena`, y responde una sesión opaca: `token` y `expiraEn` |
| `POST /api/auth/logout` | revoca la sesión con la que va firmada la petición; `204` |
| `GET /api/me` | quién llama, tal como lo resolvió la API: `id`, `email`, `nombre`, `roles` |

Las contraseñas son hashes argon2id en `credenciales`, así que `Usuario` no lleva ningún secreto.
Un token de sesión son 256 bits aleatorios, y `sesiones` solo guarda su SHA-256. Revocar uno es un
`DELETE`, y no hay clave de firma que rotar. Un email desconocido y una contraseña equivocada
reciben el mismo `401 auth.credenciales_invalidas`, en el mismo tiempo.

```ini title=".env"
AUTH_SESSION_TTL=30d      # 30d, 12h, 90m
```

Los roles son la columna `usuarios.roles`, y valen desde la siguiente petición:

```bash
make auth/conceder EMAIL=ada@example.com ROL=admin
```

El registro está abierto. `registrar_usuario`, `login` y `logout`
(`contextos/usuario/aplicacion/src/`) y `contextos/usuario/rest/src/auth/` son tuyos: cierra ahí
el registro o añade reglas.
</TabItem>
</Tabs>

## Protegido por defecto

En un proyecto con auth, toda ruta del scaffold está protegida. Un handler que recibe
`auth: BearerAuth` responde `401 auth.no_autenticado` antes de ejecutarse cuando el token falta,
es desconocido o ha caducado. Las rutas abiertas y los roles son flags del scaffold:

```bash
puerto generar scaffold Producto \
  --publico listar_productos,obtener_producto \
  --rol borrar_producto=admin \
  -- nombre:String precio:i64 sku:String!
```

```rust title="contextos/producto/rest/src/rutas.rs (fragmento)"
/// Borra: Producto
#[oai(path = "/productos/:id", method = "delete", tag = "ApiTags::Producto")]
#[requiere_rol("admin")]
async fn borrar(&self, auth: BearerAuth, id: Path<Uuid>) -> RespuestaBorrarProducto {
    match self
        .borrar_producto
        .ejecutar(ParamsBorrarProducto {
            actor: auth.0,
            id: IdProducto::from_uuid(id.0),
        })
        .await
    // …
```

`#[requiere_rol("admin")]` añade una comprobación `403 auth.prohibido` al principio del handler.
Dos roles en una ruta significan que quien llama necesita los dos. Los flags quedan en
`puerto.toml`:

```toml
[[entidad]]
nombre = "Producto"
publicos = ["listar_productos", "obtener_producto"]

[entidad.roles]
borrar_producto = ["admin"]
```

`puerto validar` comprueba que `rutas.rs` sigue diciendo lo mismo que el manifiesto. Cambia los
dos a la vez.

## Campos privados

Una ruta pública responde a todo el mundo, así que el email de un jugador en una lista pública es
de todo el mundo. Márcalo como privado:

```bash
puerto generar scaffold Jugador \
  --publico listar_jugadores,obtener_jugador \
  --privado email \
  -- nombre:String email:String dorsal:i64
```

El campo es opcional en `DtoJugador`. Una ruta pública que responde la entidad recibe
`auth: BearerAuthOpcional`: quien llama con sesión recibe la entidad entera, y quien llama sin ella
recibe `DtoJugador::from_dominio_publico`, sin el campo. `BearerAuthOpcional` nunca responde `401`:
sin token, con un token que el autenticador rechaza o con uno que no puede comprobar, no hay
llamante. Las rutas protegidas responden la entidad entera, porque quien las llama siempre tiene
sesión. Los campos privados son texto (`String`, `Option<String>` o un objeto valor sobre uno de
ellos); el flag queda en `[[entidad.campos]] privado = true`.

## Reglas que dependen de los datos

«Solo puede editarlo quien lo creó» no es un atributo: depende de la fila. Los casos de uso
protegidos reciben a quien llama como `actor: Principal` (`id_usuario`, `sujeto`, `email`,
`nombre`, `roles`) y deciden. Con un campo `propietario:Uuid` en la entidad:

```rust
if producto.propietario != params.actor.id_usuario {
    return Err(ErrorProducto::Prohibido);   // 403 producto.prohibido
}
```

El dominio ve un `Principal`, nunca un token. Los tests construyen uno con
`puerto_nucleo::auth::dobles::MadrePrincipal`, y los tests de rutas inician sesión con un
`MockAutenticador`.

## El frontend

`useAuth()` da `{ usuario, puede(rol), login, logout }`, donde `usuario` sale de `GET /me`. La
tabla de rutas generada envuelve cada pantalla no pública en `<RequiereAuth>`, que manda a iniciar
sesión a quien no la tiene, como hace un `401` de cualquier llamada. Las pantallas generadas
ocultan las acciones que los roles del usuario no permiten, pero decide la API: su `403` llega a la
alerta como `auth.prohibido`.

| | OIDC | Local |
|---|---|---|
| Inicio de sesión | Authorization Code + PKCE (`oidc-client-ts`); vuelve a `/auth/callback` | las páginas `/login` y `/registro` |
| Dónde va el token | en memoria; una recarga vuelve a pasar por el proveedor | `localStorage`; Cerrar sesión lo revoca |

Esas páginas van fuera del menú de la app, en una página de acceso con la marca del proyecto. Con
la sesión iniciada, el menú de usuario lleva a `/perfil`, que muestra lo que responde `GET /me`.

## Errores

| Estado | Código | Cuándo |
|---|---|---|
| 401 | `auth.no_autenticado` | sin token, o con uno inválido o caducado |
| 401 | `auth.credenciales_invalidas` | login local con un email o una contraseña equivocados |
| 403 | `auth.prohibido` | a quien llama le falta un rol que pide `#[requiere_rol]` |
| 403 | `<entidad>.prohibido` | una regla del propio caso de uso rechazó a quien llama (`producto.prohibido`) |
| 409 | `usuario.duplicado` | registro local con un email que ya tiene cuenta |
| 422 | `usuario.validacion.email_invalido`, `usuario.validacion.contrasena_demasiado_corta` | registro local con un email incorrecto o una contraseña de menos de 12 caracteres |
| 503 | `auth.no_disponible` | no se pudo llegar al proveedor |
