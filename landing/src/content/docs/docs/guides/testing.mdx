Un scaffold recién hecho pasa `make test`, `make lint` y `make format`, y no es porque tenga pocos
tests. Cada pieza generada trae los tests que fijan su comportamiento, en el crate donde vive ese
comportamiento.

| Capa | Tests | Contra |
|---|---|---|
| Modelo de dominio | las reglas de `new`, el análisis de los objetos valor | nada |
| Errores | cada brazo de `From<ErrorRepositorio>` | nada |
| Casos de uso | el éxito y cada camino de fallo | un doble del repositorio o `UnitOfWorkFactoryGrabadora` |
| Repositorios | guardar, buscar, paginar, borrado lógico, unicidad | en memoria, o un Postgres real con `#[sqlx::test]` |
| Rutas | el estado de cada resultado, sobre el `OpenApiService` real | dobles de los casos de uso |
| Errores HTTP | un test por variante: su estado y su código | nada |
| Consumidores | confirma, confirma dos veces (idempotencia), payload inválido | sobres construidos con una madre |
| Correo | cada plantilla se renderiza | nada |
| Pantallas | lista, detalle, formulario, errores bajo los campos | `apiFalsa`, la API falsa en memoria |
| Especificación | `docs/api/openapi.json` es igual a la especificación real | dobles de los casos de uso |

## Convenciones

Los tests de Puerto, y los que su `AGENTS.md` os pide escribir a ti y a tu agente, siguen una
forma:

```rust
#[tokio::test]
async fn deberia_rechazar_el_precio_cuando_no_es_positivo() {
    // Preparar
    // Actuar
    // Comprobar
}
```

- Los nombres dicen `deberia_<comportamiento_esperado>_cuando_<escenario>`.
- `// Preparar`, `// Actuar`, `// Comprobar`, en ese orden.
- Los tests viven en el fichero que prueban, en un `#[cfg(test)] mod tests`.
- TDD: primero el test que falla, después el mínimo código que lo hace pasar.
- Ningún `unwrap()` ni `expect()` fuera de los tests.

## Los dobles vienen con los puertos

Cada puerto es un trait, y cada fichero de trait lleva su doble de `mockall` en un módulo
`dobles` tras `#[cfg(any(test, feature = "pruebas"))]`:
`dominio_producto::repositorio::dobles::MockRepositorioProducto`,
`aplicacion_producto::crear_producto::dobles::MockCrearProducto`,
`dominio_correo::bienvenida::dobles::MockEnviadorCorreoBienvenida`. Un crate que usa los dobles de
otro activa la feature `pruebas` en sus `[dev-dependencies]`, así que los tests de
`rest_producto` usan los dobles de `aplicacion_producto` sin meterlos en el binario.

```rust
let mut repositorio_doble = MockRepositorioProducto::new();
repositorio_doble.expect_buscar_por_id().returning(|_| Ok(None));
repositorio_doble.expect_guardar().never();
```

En un proyecto con eventos, los casos de uso que escriben se prueban con
`UnitOfWorkFactoryGrabadora` (`dominio_producto::unit_of_work::dobles`), que guarda lo que se
guardó, qué eventos se registraron y si se confirmó:

```rust
let grabado = uow_factory.grabado();
assert!(grabado.confirmado);
assert_eq!(grabado.guardados.len(), 1);
```

## Las madres

`contextos/producto/dominio/src/pruebas/madres.rs` construye entidades válidas, así que un test
solo dice lo que le importa:

```rust
let producto = MadreProducto::aleatorio();
let barato = MadreProducto::new().con_precio(1).construir();
let varios = MadreProducto::aleatorios(5);
let props = MadreProducto::new().con_nombre_vacio().construir_props();
```

Cada campo tiene `.con_<campo>(valor)`, y los campos `String` obligatorios también
`.con_<campo>_vacio()`.

La madre es también de donde sacan sus valores válidos los tests generados: los del modelo, los
de los casos de uso (`let props = MadreProducto::new().construir_props();`, y los params desde
`props`) y los de los repositorios. Una regla que rechaza un valor por defecto, `puntos <= 100`
contra un `puntos` de `42`, se arregla en un solo sitio: el valor por defecto de la madre. La
siembra de los repositorios solo guarda su propio valor donde una fila guardada lo necesita: un
valor nuevo por cada campo único, y una fecha en segundos enteros que Postgres guarda exacta.
Las madres están tras la misma feature `pruebas` que los dobles
(`dominio_producto::pruebas::madres::MadreProducto`), así que los tests de rutas y del worker
construyen con ellas lo que devuelven, en lugar de un segundo juego de datos de prueba. El frontend
tiene las suyas (`MadreProducto` en `web/src/pruebas/producto.ts`), junto a `apiFalsa`, el falso
en memoria de la API generada con el que hablan HTTP todos los tests de pantallas.

## Ejecutarlos

```bash
make test                   # cargo nextest sobre el workspace, y después bun test en web/
make test/dominio           # todos los crates dominio_*
make test/aplicacion        # todos los crates aplicacion_*
make test/infraestructura   # todos los crates infra_*; necesita la base de datos en los proyectos --db
make lint                   # clippy -D warnings, y en web/ el chequeo de tipos, Biome y la regla de dependencias
make format                 # cargo fmt --check
```

Un solo crate es `cargo test -p dominio_producto`.

En un proyecto `--db`, los tests de los repositorios corren contra una base de datos real, así
que arráncala antes con `make docker-compose/up`. Cada uno es un
`#[sqlx::test(migrator = "migrador::MIGRADOR")]`: una base de datos desechable por test, migrada
con el único migrador del proyecto, así que ningún test lleva su propia copia de las migraciones.
Las filas que necesita un test salen del `pruebas::siembra::sembrar` del crate.

## Datos de ejemplo

Para probar la app a mano, `puerto nuevo` escribe una vez `scripts/sembrar.sh`, que es tuyo, y
`make sembrar` lo ejecuta contra la API en marcha con el `.env` cargado. Trae los helpers: `peticion`
(imprime el estado y el cuerpo), `crear` (devuelve el id, o sale si no es un `201`) y, según el
auth, `sesion` y `conceder`:

```bash title="scripts/sembrar.sh (fragmento)"
ADA=$(sesion ada@aforo.es "Ada Lovelace")
conceder ada@aforo.es admin
SALA=$(crear /salas "$ADA" '{"nombre":"La Ribera","ciudad":"Madrid","direccion":"C/ Embajadores 41","capacidad":450,"contacto":"booking@laribera.es"}')
peticion GET "/salas/$SALA"
```

Necesita `curl` y `jq`. Sobre una base de datos con datos, una segunda pasada choca (`409`) con la
primera: `CONFIRM=DESTRUIR make db/reiniciar` la vacía sin preguntar.

<Aside type="note" title="Cómo se prueba Puerto">
La batería de Puerto genera proyectos en todas las combinaciones (en memoria, `--db`, eventos sobre
`db` y sobre Kafka, auth, web) y ejecuta su clippy, sus tests y su `fmt --check`, además de tests
de mutación sobre su lógica de decisión. Si un proyecto generado fallara su propio `make test`,
el CI de Puerto fallaría antes.
</Aside>
