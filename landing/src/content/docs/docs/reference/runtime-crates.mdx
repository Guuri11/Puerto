Lo que es igual en todos los proyectos y no está pensado para editarse no se genera: es un crate.
El runtime sigue la misma regla de dependencias que tu proyecto, así que está partido por capas en
lugar de ser un solo crate con features
([ADR-0017](/docs/decisions/adr/0017-runtime-crates-next-to-the-generator/)). El framework también
es hexagonal: `puerto-nucleo` tiene los puertos, y los demás crates son adaptadores. Su API está en
castellano, como el código que la llama.

| Crate | Se encarga de | Lo usan | Está cuando |
|---|---|---|---|
| [`puerto-nucleo`](https://docs.rs/puerto-nucleo) | `ErrorRepositorio`, `PeticionPagina` / `Pagina<T>`; el sobre de los eventos (`SobreEvento`), `ManejadorEvento`, la política de entrega y los puertos del transporte; los puertos del correo (`Correo`, `EnviadorCorreo`, `CorreosEnviados`); el puerto de auth (`Autenticador`) y `Principal` | todos los crates, también el dominio: sin driver, sin runtime, sin E/S | siempre |
| [`puerto-web`](https://docs.rs/puerto-web) | el servidor (`App`), `Config`, CORS, las sondas de salud, el apagado ordenado, `RespuestaError`, `BearerAuth`, `BearerAuthOpcional`, `#[requiere_rol]` | los crates `rest_<c>` y `api` | siempre |
| [`puerto-sqlx`](https://docs.rs/puerto-sqlx) | el pool, las migraciones al arrancar, la sonda de disponibilidad, `mapear_error_sqlx`; la unidad de trabajo, el outbox y el transporte `db`; el registro de correos enviados; las sesiones y credenciales locales | los crates `infra_<c>` y los binarios | `--db` |
| [`puerto-eventos`](https://docs.rs/puerto-eventos) | el worker: el relay del outbox, los bucles de consumo, sus sondas de salud y su apagado | `worker` | `--eventos` |
| [`puerto-kafka`](https://docs.rs/puerto-kafka) | el publicador y la suscripción de Kafka | `worker` | `--eventos kafka` |
| [`puerto-correo`](https://docs.rs/puerto-correo) | el adaptador SMTP, el renderizador de plantillas, `enviar_una_vez` | `infra_correo`, `worker` | un correo |
| [`puerto-auth`](https://docs.rs/puerto-auth) | feature `oidc`: `AutenticadorOidc`; feature `local`: el hash argon2id | `api` | `--auth` |
| [`puerto-macros`](https://docs.rs/puerto-macros) | `#[requiere_rol]` | a través de `puerto-web` | `--auth` |

## Cómo depende de ellos un proyecto

Una vez, en el `Cargo.toml` raíz, en la minor que generó el proyecto:

```toml title="Cargo.toml"
[workspace.dependencies]
puerto-nucleo = "0.23"
puerto-web = "0.23"
puerto-sqlx = "0.23"
```

Y cada crate hereda lo que su capa puede usar:

```toml title="contextos/producto/rest/Cargo.toml"
[dependencies]
puerto-nucleo = { workspace = true }
puerto-web = { workspace = true }

[dev-dependencies]
puerto-nucleo = { workspace = true, features = ["pruebas"] }
```

`pruebas` expone dobles de test (`MockAutenticador`, `MadrePrincipal`, `EnviadorCorreoGrabador`,
`CorreosEnviadosEnMemoria`) a los tests de un proyecto y los deja fuera de sus binarios.

## El contrato

- **A la par.** La CLI y todos los crates del runtime comparten una versión. `puerto 0.23` genera
  proyectos que piden la `0.23`, y `puerto validar` avisa cuando se separan.
- **La app llama al runtime.** No hay un trait `Hooks` que implementar ni un contenedor que llame a
  tu código: `main.rs` y `bootstrap.rs` llaman a piezas del runtime, en Rust normal que puedes
  seguir.
- **`#[non_exhaustive]` desde el primer día.** Todo enum y struct público que puedas recibir puede
  crecer sin un cambio incompatible.
- **Los puertos en `puerto-nucleo`, los adaptadores en sus crates.** Para cambiar un adaptador,
  implementa el puerto. Un proyecto solo compila los adaptadores que usa: un proyecto sin Kafka
  nunca compila `rdkafka`.
- **Los traits que implementas para tus tipos se quedan en tu proyecto.** La orphan rule de Rust
  impide que un crate `rest_<c>` implemente el `IntoRespuestaError` de `puerto-web` para el error
  de su dominio, así que cada `errores.rs` exporta en su lugar una función libre,
  `a_respuesta_error` ([ADR-0023](/docs/decisions/adr/0023-crates-por-contexto-y-capa/)).
