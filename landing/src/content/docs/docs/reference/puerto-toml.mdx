---
title: El manifiesto puerto.toml
description: El esquema completo de puerto.toml, el manifiesto que leen y actualizan los generadores - proyecto, entidades, campos, objetos valor, consumidores y correos.
---

`puerto.toml` es la fuente de verdad de un proyecto. Lo escriben los generadores; `cableado`,
`bootstrap.rs`, `eventos.rs`, `registro.rs` y los ficheros generados del frontend salen de él; y
`puerto validar` comprueba el código contra él. Puedes editarlo a mano; ejecuta después
`puerto generar bootstrap` y `puerto validar`.

Un ejemplo completo, de un proyecto con base de datos, eventos, auth y un correo:

```toml title="puerto.toml"
[proyecto]
nombre = "tienda"
db = true
web = true
eventos = "db"
auth = "local"

[[entidad]]
nombre = "Cliente"
casos_de_uso = [
    "crear_cliente",
    "obtener_cliente",
    "listar_clientes",
    "actualizar_cliente",
    "borrar_cliente",
]
db = true

[[entidad.campos]]
nombre = "email"
tipo = "String"
objeto_valor = "Email"

[[entidad.campos]]
nombre = "nombre"
tipo = "String"

[[entidad]]
nombre = "Producto"
casos_de_uso = [
    "crear_producto",
    "obtener_producto",
    "listar_productos",
    "actualizar_producto",
    "borrar_producto",
    "publicar_producto",
]
db = true
publicos = [
    "listar_productos",
    "obtener_producto",
]
eventos = ["producto_publicado"]

[entidad.roles]
borrar_producto = ["admin"]

[[entidad.campos]]
nombre = "nombre"
tipo = "String"

[[entidad.campos]]
nombre = "sku"
tipo = "String"
unico = true

[[entidad]]
nombre = "Pedido"
casos_de_uso = [
    "crear_pedido",
    "obtener_pedido",
    "listar_pedidos",
    "actualizar_pedido",
    "borrar_pedido",
]
db = true

[[entidad.campos]]
nombre = "cliente_id"
tipo = "Uuid"
referencia = "Cliente"

[[entidad.campos]]
nombre = "estado"
tipo = "String"
objeto_valor = "Estado"
clase_objeto_valor = "enum"
variantes = [
    "Pendiente",
    "Confirmado",
    "Cancelado",
]

[[objeto_valor]]
nombre = "Email"
tipo = "String"

[[consumidor]]
nombre = "avisar_producto_nuevo"
eventos = [
    "producto_creado",
    "producto_publicado",
]

[[correo]]
nombre = "bienvenida"
tras = ["cliente_creado"]
```

## `[proyecto]`

| Clave | Tipo | La pone | Significa |
|---|---|---|---|
| `nombre` | string | `nuevo --nombre` | El nombre del proyecto: crates, base de datos, topics |
| `db` | bool | `nuevo --db` | Postgres con SQLx. Si falta, `false` |
| `web` | bool | `nuevo` (por defecto), `--sin-web` | El frontend React en `web/` |
| `eventos` | `"db"` \| `"kafka"` | `nuevo --eventos` | Los eventos de dominio y su transporte. Necesita `db` |
| `auth` | `"oidc"` \| `"local"` | `nuevo --auth` | El modo de autenticación. `local` necesita `db` |
| `portada` | bool | `nuevo --portada` | Un SaaS con portada pública: la portada en `/` y la app debajo de `ruta_app`. Necesita `web` |
| `ruta_app` | string | `nuevo --ruta-app` | Dónde va la app bajo la portada; `/panel` por defecto. Solo con `portada` |

## `[[entidad]]`

| Clave | Tipo | La pone | Significa |
|---|---|---|---|
| `nombre` | string | `scaffold`, `dominio` | En PascalCase. Cada entidad es un contexto, `contextos/<snake>/` |
| `casos_de_uso` | string[] | `scaffold`, `caso-de-uso` | Cada caso de uso que construye `cableado`. Con los cinco CRUD es una entidad CRUD, con rutas y pantallas |
| `db` | bool | `scaffold` en un proyecto `db` | Repositorio Postgres en lugar de en memoria |
| `publicos` | string[] | `scaffold --publico` | Proyectos con auth: los casos de uso cuyas rutas no piden token |
| `roles` | tabla | `scaffold --rol` | Proyectos con auth: `caso_de_uso = ["rol", …]`; quien llama necesita todos |
| `eventos` | string[] | `generar evento` | Tipos de evento propios, además de `_creado`, `_actualizado`, `_borrado` |
| `unicos` | string[][] | `scaffold --unico`, `dominio --unico` | Únicos sobre varios campos: un índice único parcial cada uno, que también comprueba el repositorio en memoria |
| `orden` | string[] | `scaffold --orden`, `dominio --orden` | El orden de la lista: campos propios, `-` para descendente; después, lo más nuevo primero |

## `[[entidad.campos]]`

| Clave | Tipo | Significa |
|---|---|---|
| `nombre` | string | En snake_case |
| `tipo` | string | `String`, `i64`, `f64`, `bool`, `Uuid`, `DateTime<Utc>`, `HashMap<String, String>`, o `Option<…>` / `Vec<…>` de ellos. Mira [Tipos de campo](/docs/reference/field-types/) |
| `unico` | bool | Un índice único parcial, y un `409` ante un duplicado |
| `privado` | bool | Proyectos con auth, campos de texto: las rutas públicas solo lo dan a quien tiene sesión (`scaffold --privado`) |
| `objeto_valor` | string | El objeto valor que lo envuelve, local o compartido |
| `clase_objeto_valor` | `"enum"` | Un objeto valor enum; entonces `tipo` es `String` |
| `variantes` | string[] | Sus variantes en PascalCase |
| `referencia` | string | Otra entidad CRUD cuyo id guarda este campo; entonces `tipo` es `Uuid` u `Option<Uuid>`. Una clave foránea en los proyectos `db`. Mira [Referencias](/docs/reference/field-types/#referencias) |

## `[[objeto_valor]]`

Los objetos valor compartidos, que declara `generar objeto-valor`: `nombre` (en PascalCase) y
`tipo` (su primitivo interno). Viven en el crate `nucleo`. Un campo que nombra uno sin tipo usa
este.

## `[[consumidor]]`

Proyectos con eventos. Lo escribe `generar consumidor`: `nombre` (en snake_case, el fichero del
manejador y su grupo de consumidores) y `eventos` (los tipos de evento que maneja). Un consumidor
cuyo fichero falta hace fallar `validar` y que `generar bootstrap` se niegue.

## `[[correo]]`

Lo escribe `generar correo`: `nombre`, y `tras` cuando el worker lo envía tras unos eventos.

## Lo que comprueba `puerto validar`

- Los nombres: entidades en PascalCase, campos y casos de uso en snake_case, ninguna palabra clave
  de Rust, ninguna palabra reservada de SQL en los proyectos `db`, ningún nombre que ya usen el
  código generado u otro contexto.
- Los tipos: cada tipo de campo es uno que genera Puerto, y cada objeto valor compartido existe.
- La coherencia: `eventos` y `auth = "local"` necesitan `db`; cada entidad, consumidor y correo
  declarados tiene sus ficheros; en los proyectos con web, cada entidad CRUD tiene sus pantallas;
  en los proyectos con auth, el `BearerAuth` y el `#[requiere_rol]` de cada ruta coinciden con
  `publicos` y `roles`; cada `referencia` nombra otra entidad CRUD declarada, es un `Uuid` u
  `Option<Uuid>` y no cierra un ciclo entre contextos; cada grupo de `unicos` y cada clave de
  `orden` nombran campos simples y obligatorios de la entidad; `privado` solo en campos de texto
  de un proyecto con auth.
- El runtime: un aviso por cada crate `puerto-*` que esté en otra minor que la CLI.
