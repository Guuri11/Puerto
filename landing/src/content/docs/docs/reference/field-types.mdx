---
title: Tipos de campo
description: Todos los tipos de campo que genera Puerto, con su sintaxis en la CLI y en qué se convierten en Rust, en Postgres, en el JSON y en el formulario generado.
---

Un campo se declara una vez, como `nombre:Tipo` tras el `--` de `generar scaffold` o de `generar
dominio`, y Puerto lleva su tipo por todas las capas. La decisión de cada tipo se toma en un solo
sitio del generador, `generators/types.rs`
([ADR-0011](/docs/decisions/adr/0011-templates-own-shape-types-own-decisions/)).

## Primitivos

| CLI | Rust | Postgres | TypeScript | Control del formulario |
|---|---|---|---|---|
| `titulo:String` | `String` | `TEXT NOT NULL` | `string` | input de texto, `required` |
| `cantidad:i64` | `i64` | `BIGINT NOT NULL` | `number` | input numérico |
| `valoracion:f64` | `f64` | `DOUBLE PRECISION NOT NULL` | `number` | input numérico, `step=any` |
| `activo:bool` | `bool` | `BOOLEAN NOT NULL` | `boolean` | checkbox |
| `id_externo:Uuid` | `Uuid` | `UUID NOT NULL` | `string` | input de texto, `required` |
| `vence_en:DateTime` | `DateTime<Utc>` | `TIMESTAMPTZ NOT NULL` | `string` (ISO 8601) | `datetime-local` |
| `meta:map` | `HashMap<String, String>` | `JSONB NOT NULL DEFAULT '{}'` | `Record<string, string>` | textarea, una línea `clave=valor` por entrada |

`DateTime` y `map` son atajos: el manifiesto guarda `DateTime<Utc>` y `HashMap<String, String>`.

## Opcionales y repetidos

| CLI | Rust | Postgres | TypeScript |
|---|---|---|---|
| `nota:opt:String` | `Option<String>` | `TEXT` (admite nulos) | `string`, opcional |
| `stock:opt:i64` | `Option<i64>` | `BIGINT` | `number`, opcional |
| `puntuacion:opt:f64` | `Option<f64>` | `DOUBLE PRECISION` | `number`, opcional |
| `hecho:opt:bool` | `Option<bool>` | `BOOLEAN` | `boolean`, opcional |
| `visto_en:opt:DateTime` | `Option<DateTime<Utc>>` | `TIMESTAMPTZ` | `string`, opcional |
| `etiquetas:vec:String` | `Vec<String>` | `TEXT[] NOT NULL DEFAULT '{}'` | `string[]` |
| `cantidades:vec:i64` | `Vec<i64>` | `BIGINT[] NOT NULL DEFAULT '{}'` | `number[]` |

Un campo opcional no es `required` en el formulario, y un input vacío no se manda; cuando falta,
la API lo devuelve como `null`. Un vector es un input de texto separado por comas.

## Objetos valor

Un objeto valor envuelve un primitivo en un tipo propio, así que el dominio puede validarlo una vez
y nada puede pasar una cadena suelta donde va un `Email`. Mira
[Objetos valor](/docs/guides/value-objects/).

| CLI | Rust (dominio) | En el JSON |
|---|---|---|
| `email:Email:String` | `Email(String)` | `string` |
| `importe:Importe:f64` | `Importe(f64)` | `number` |
| `apodo:Apodo:opt:String` | `Option<Apodo>` | `string`, opcional |
| `etiquetas:Etiqueta:vec:String` | `Vec<Etiqueta>` | `string[]` |
| `estado:Estado:enum:Borrador/Pagado` | `enum Estado { Borrador, Pagado }` | `string` (un `<select>` con `Borrador` y `Pagado`) |
| `email:Email` | el `Email` compartido | su tipo interno |

La última fila usa un objeto valor **compartido**, declarado una vez con
`puerto generar objeto-valor Email String` y que cualquier entidad puede usar.

## Referencias

Un campo puede guardar el id de otra entidad
([ADR-0022](/docs/decisions/adr/0022-references-are-typed-ids-checked-by-foreign-keys/)): un
`Pedido` que pertenece a un `Cliente` guarda el id del cliente, nunca el cliente.

| CLI | Rust (dominio) | Postgres | En el JSON | Control del formulario |
|---|---|---|---|---|
| `cliente_id:ref:Cliente` | `IdCliente` | `UUID NOT NULL REFERENCES clientes (id)` | `string` (uuid) | `<select>` de clientes |
| `revisor_id:ref:opt:Cliente` | `Option<IdCliente>` | `UUID REFERENCES clientes (id)` | `string`, opcional | `<select>` con una opción vacía |

- El objetivo tiene que ser una entidad CRUD ya generada, y no la propia entidad. `!` (uno a uno)
  vale en `ref:`, no en `ref:opt:`.
- El dominio guarda el tipo de id del objetivo, así que un `IdProducto` no puede ir donde se
  espera un `IdCliente`, y `dominio_pedido` depende de `dominio_cliente`. Las filas y los DTO
  guardan un `Uuid`. Dos contextos que se referencian entre sí serían un ciclo entre crates, así
  que `scaffold` rechaza la referencia que lo cierra.
- En los proyectos `--db` la clave foránea comprueba que el objetivo existe: una escritura que
  nombra uno que no existe es un `422` con `<entidad>.validacion.cliente_id_no_encontrado`, que se
  muestra bajo el campo. El caso de uso no busca antes el cliente. Los proyectos en memoria no
  comprueban nada.
- La lista filtra por cada referencia: `GET /pedidos?clienteId=…`.
- El borrado es lógico, así que un pedido sigue apuntando a su cliente borrado: rechazar el
  borrado o propagarlo es decisión del proyecto.

Todavía no: una referencia a la propia entidad, muchos a muchos (`vec:ref:`) y `ref:Usuario`.

## Únicos

Añade `!` a cualquier campo: `sku:String!`, `email:Email:String!`. En Postgres se convierte en un
índice único **parcial** con nombre, así que una fila borrada de forma lógica no sigue ocupando su
valor ([ADR-0003](/docs/decisions/adr/0003-unique-indexes-are-partial/)):

```sql
CREATE UNIQUE INDEX productos_sku_key ON productos (sku) WHERE borrado = false;
```

Un duplicado es un `409` con `<entidad>.duplicado`, venga de Postgres o del repositorio en memoria.

## Las columnas que tiene toda entidad

`id` (`UUID PRIMARY KEY`, el `Id<Entidad>` propio de la entidad en el dominio), `creado_en`,
`actualizado_en`, `borrado` y `borrado_en`. El borrado es lógico: toda consulta generada filtra
`WHERE borrado = false`.

## Los nombres que se rechazan

Puerto rechaza un nombre cuando no compilaría o no migraría, en el comando que lo introduce y no en
`cargo build`:

- Los nombres de campo que ya tiene toda entidad (`id`, `creado_en`, `actualizado_en`, `borrado`,
  `borrado_en`) y las palabras clave de Rust (`type`, `match`…). Los nombres de campo van en
  snake_case.
- En los proyectos `--db`, las palabras reservadas de PostgreSQL como nombre de campo (`order`,
  `user`, `desc`…). Un proyecto sin base de datos puede usarlas
  ([ADR-0005](/docs/decisions/adr/0005-sql-reserved-words-only-in-db-projects/)).
- Los nombres de entidad que chocarían con un tipo que ya usa el código generado (`Error`,
  `String`, `Option`, `Uuid`…) o con un contexto que el proyecto ya tiene: `Correo`, el contexto de
  los correos, y en los proyectos con auth `Usuario`, `Me` y `Auth`. Los nombres de entidad van en
  PascalCase.
