## Por qué no MVC

MVC es una buena forma de empezar y una mala forma de crecer. Las reglas de negocio acaban donde
era cómodo escribirlas: un callback del modelo, una comprobación en el controlador, un scope de
consulta. Probar una regla pasa a pedir una base de datos y una petición HTTP, y cambiar la base de
datos obliga a tocar las reglas.

Puerto genera la alternativa desde el primer comando. **Domain-Driven Design** pone el vocabulario
(entidades, objetos valor, repositorios, eventos de dominio) y **Clean Architecture**, también
llamada hexagonal o de puertos y adaptadores, pone la regla que lo mantiene limpio.

## La regla de dependencias

<LayerStack />

Cada entidad es un contexto con cuatro crates, y las dependencias solo apuntan hacia dentro:

```txt
rest_<c> → aplicacion_<c> → dominio_<c> → nucleo, puerto-nucleo
infra_<c> → dominio_<c>
presentacion/ (cableado, api, worker) → todos ellos
```

- **`dominio_<c>`** tiene el modelo, los objetos valor, los errores y el **puerto** del
  repositorio. Depende de `nucleo` (los objetos valor compartidos) y de `puerto-nucleo`, y de
  ningún driver de base de datos ni framework HTTP. Sus tests solo necesitan `cargo test`.
- **`aplicacion_<c>`** tiene los casos de uso, un fichero cada uno: params, trait,
  implementación, doble y tests. Conoce su dominio y nada más.
- **`infra_<c>`** tiene los **adaptadores** que implementan los puertos del dominio: un
  repositorio en memoria o Postgres, una unidad de trabajo. Conoce el dominio, nunca los casos de
  uso ni las rutas.
- **`rest_<c>`** es el HTTP: rutas, DTO, enums de respuesta, errores HTTP. Es un adaptador más,
  el que convierte peticiones en llamadas a casos de uso. Conoce la aplicación y el dominio, nunca
  `infra_<c>`.
- **`presentacion/`** es la raíz de composición. `cableado` construye los repositorios y los
  casos de uso de cada contexto; `api`, y `worker` en los proyectos con eventos, son los
  binarios. Solo ellos dependen de los crates `infra_*`.

No es una pauta que se mantiene a base de disciplina: cada capa de cada contexto es su propio
crate, y un crate no puede importar aquello de lo que no depende. Un modelo de dominio que intenta
usar `sqlx` no compila, y tampoco una ruta que intenta llegar al repositorio Postgres. Una
referencia entre entidades (`cliente_id:ref:Cliente`) hace que `dominio_pedido` dependa de
`dominio_cliente`, y Cargo rechaza un ciclo, así que el mapa entre contextos también lo comprueba
el compilador ([ADR-0023](/docs/decisions/adr/0023-crates-por-contexto-y-capa/)).

## Una petición, de punta a punta

`POST /api/productos` con `{"nombre":"Lampara","precio":4900,"sku":"LMP-01"}`, en un proyecto
`--db`:

1. **`rest_producto`**. `ApiProducto::crear` recibe `Json<PeticionCrearProducto>`, un DTO.
   Construye `ParamsCrearProducto` y llama a `self.crear_producto.ejecutar(params)`.
   `crear_producto` es un `Arc<dyn CrearProducto>`: la ruta depende de un puerto, no de una
   implementación ([ADR-0012](/docs/decisions/adr/0012-presentation-holds-use-case-ports/)).
2. **`aplicacion_producto`**. `CrearProductoImpl` construye la entidad con
   `Producto::new(props)`, donde se ejecutan las reglas del dominio, y llama a
   `self.repositorio.guardar(&entidad)` sobre un `Arc<dyn RepositorioProducto>`.
3. **`infra_producto`**. `RepositorioProductoPostgres::guardar` escribe la fila. Un único violado
   vuelve de Postgres como `ErrorRepositorio::Duplicado`, convertido una sola vez en
   `puerto-sqlx` ([ADR-0015](/docs/decisions/adr/0015-repositories-return-one-repository-error/)).
4. **De vuelta.** `ErrorProducto::Duplicado` llega a la ruta, y `a_respuesta_error` en
   `errores.rs` lo convierte en un `409` con `{"codigo":"producto.duplicado"}`. No tiene brazo
   comodín: una variante de error nueva no compila hasta que alguien decide su estado
   ([ADR-0007](/docs/decisions/adr/0007-error-contract-code-in-name-422/)).

El dominio nunca ve JSON, y la ruta nunca ve SQL.

## Cablear sin contenedor

¿Quién decide que `ApiProducto::crear_producto` es un `CrearProductoImpl` sobre un
`RepositorioProductoPostgres`? Un crate: `presentacion/cableado`, la **raíz de composición**.
Puerto lo genera desde `puerto.toml`, como Rust normal que puedes leer:

```rust title="presentacion/cableado/src/lib.rs (fragmento, --db)"
pub fn construir(pool: &sqlx::PgPool) -> CasosDeUso {
    let repositorio: Arc<dyn RepositorioProducto> =
        Arc::new(RepositorioProductoPostgres::new(pool.clone()));
    CasosDeUso {
        crear_producto: Arc::new(CrearProductoImpl {
            repositorio: Arc::clone(&repositorio),
        }),
        obtener_producto: Arc::new(ObtenerProductoImpl {
            repositorio: Arc::clone(&repositorio),
        }),
        // listar_productos, actualizar_producto, borrar_producto: lo mismo
    }
}
```

`cableado` no sabe nada de HTTP. `presentacion/api/src/generado/bootstrap.rs` llama a
`cableado::producto::construir(&pool)`, le da cada caso de uso a `ApiProducto` y monta las rutas.
No hay contenedor en ejecución, ni reflexión, ni macros que registren rutas a tus espaldas. «Ir a
la definición» funciona en todas partes, para ti y para un agente. El precio es que nunca editas
estos ficheros a mano: cambia `puerto.toml` y ejecuta `puerto generar bootstrap`.

Tu propio cableado, middleware de más o rutas fuera del servicio OpenAPI va en
`presentacion/api/src/app.rs`, un fichero que Puerto escribe una vez y no vuelve a tocar.

## El frontend es presentación

`web/` es la capa de presentación y nada más
([ADR-0025](/docs/decisions/adr/0025-el-frontend-es-presentacion/)): las reglas viven en el
backend. Un contenedor llama al cliente tipado de la API y le pasa a su vista los DTO de la
especificación OpenAPI; una vista solo recibe props. dependency-cruiser comprueba esa frontera en
`make web/lint`: una vista que llama a la API no pasa. La especificación OpenAPI es el contrato
entre las dos mitades. Mira [El frontend web](/docs/guides/web/).

<Aside type="note" title="No todo es una capa">
Puerto no genera una capa que estaría vacía. Un caso de uso CRUD en el frontend solo delegaría en
la API, así que no hay dominio, casos de uso ni adaptadores en `web/`: la lógica de cliente que
aparezca se escribe a mano donde haga falta.
</Aside>

## Lo que el compilador impone por ti

| Si alguien… | …entonces | Porque |
|---|---|---|
| importa `sqlx` en un modelo de dominio | no compila | `dominio_<c>` no depende de él |
| usa el repositorio Postgres en una ruta | no compila | `rest_<c>` no depende de `infra_<c>` ([ADR-0023](/docs/decisions/adr/0023-crates-por-contexto-y-capa/)) |
| pasa un `IdCliente` donde va un `IdProducto` | no compila | los ids son newtypes generados ([ADR-0014](/docs/decisions/adr/0014-entity-ids-are-generated-newtypes/)) |
| escribe por el repositorio en un proyecto con eventos | no compila | el repositorio no tiene `guardar`; las escrituras van por la unidad de trabajo ([ADR-0018](/docs/decisions/adr/0018-domain-events-outbox-pluggable-transport/)) |
| añade una variante de error sin estado | no compila | `a_respuesta_error` es exhaustivo ([ADR-0007](/docs/decisions/adr/0007-error-contract-code-in-name-422/)) |
| quita un evento que escucha un consumidor | el worker no compila | los consumidores comparan con constantes generadas |
| cambia un DTO sin `make web/sync` | `make test` falla | un test compara la especificación exportada |
