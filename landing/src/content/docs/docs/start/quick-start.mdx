Esta página construye un catálogo pequeño: un `Producto` con un nombre, un precio y un SKU único,
servido como API REST con sus propias pantallas React. Funciona en memoria, así que solo necesitas
Rust y, para las pantallas, [Bun](https://bun.sh). Cada salida de esta página se capturó de una
ejecución real.

<Steps>

1. **Crea el proyecto.**

   ```bash
   puerto nuevo --nombre tienda --sin-db --sin-demo
   ```

   ```txt title="salida"
   ├── nucleo/          (objetos valor compartidos)
   ├── contextos/       (un crate por contexto y capa)
   ├── presentacion/    (los binarios y su cableado)
   ├── web/             (el frontend React)
   └── Cargo.toml
   ✓ Proyecto 'tienda' creado.
   ```

   `--sin-db` guarda los datos en memoria, y `--sin-demo` deja fuera la entidad de ejemplo
   `Saludo`. Sin esos dos flags, `puerto nuevo` pregunta.

2. **Genera una entidad.**

   ```bash
   cd tienda
   puerto generar scaffold Producto -- nombre:String precio:i64 sku:String!
   ```

   ```txt title="salida"
   ✓ contextos/producto/dominio/         modelo, errores, puerto del repositorio, MadreProducto
   ✓ contextos/producto/aplicacion/      crear, obtener, listar, actualizar, borrar
   ✓ contextos/producto/infraestructura/ RepositorioProductoEnMemoria
   ✓ contextos/producto/rest/            rutas, dto, respuestas, errores
   ✓ web/                                pantallas de lista, detalle y formulario
   ✓ Hecho. Sin cablear nada a mano.

   La API cambió. Siguiente: make web/sync   (exporta la especificación y regenera los tipos de la web)
   ```

   Los campos van tras `--` como `nombre:Tipo`. El `!` hace único a `sku`: un segundo producto
   con el mismo SKU se rechaza con `409 Conflict`. [Entidades y campos](/docs/guides/entities/)
   lista todos los tipos.

3. **Arranca la API.**

   ```bash
   make run
   ```

   El servidor arranca en el puerto 8080: la Swagger UI en `/`, la API bajo `/api` y las sondas de
   salud en `/health` y `/health/ready`.

4. **Llámala.**

   ```bash
   curl -X POST localhost:8080/api/productos \
     -H 'content-type: application/json' \
     -d '{"nombre":"Lampara","precio":4900,"sku":"LMP-01"}'
   ```

   ```json title="201 Created"
   {"id":"1f1d2bb9-a92d-48c4-ab78-f56cfcccdcd7","nombre":"Lampara","precio":4900,"sku":"LMP-01"}
   ```

   El mismo SKU otra vez, y después un nombre vacío:

   ```json title="409 Conflict"
   {"codigo":"producto.duplicado","mensaje":"producto.duplicado"}
   ```

   ```json title="422 Unprocessable Entity"
   {"codigo":"producto.validacion.nombre_vacio","mensaje":"producto.validacion.nombre_vacio"}
   ```

   Los errores son códigos legibles por máquina en `codigo`, y la validación del dominio es un
   422. Ese es [el contrato de errores](/docs/reference/errors/), el mismo en todo proyecto
   Puerto. Las listas van paginadas:

   ```bash
   curl 'localhost:8080/api/productos?limite=10'
   ```

   ```json title="200 OK"
   {"desplazamiento":0,"elementos":[{"id":"1f1d2bb9-a92d-48c4-ab78-f56cfcccdcd7","nombre":"Lampara","precio":4900,"sku":"LMP-01"}],"limite":10,"total":1}
   ```

5. **Abre las pantallas.** En otra terminal:

   ```bash
   make web/sync                      # exporta la especificación OpenAPI, regenera los tipos del frontend
   make web/install && make web/dev   # http://localhost:5173
   ```

   `/productos` los lista, `/productos/nuevo` crea uno, y un formulario rechazado muestra el
   mensaje junto al campo al que se refiere.

6. **Compruébalo.**

   ```bash
   make setup     # una vez: cargo-nextest y cargo-audit
   make test      # todos los tests generados: modelo, casos de uso, rutas, errores, pantallas
   make lint      # clippy -D warnings
   make format    # rustfmt --check
   ```

   Los tres pasan en un scaffold recién hecho. Esa es la base que mantienes mientras construyes.

</Steps>

## Lo que tienes ahora

- `contextos/producto/dominio/src/modelo.rs` tiene `Producto` y su tipo de id, `IdProducto`. Las
  reglas van en `Producto::new`: ya rechaza un `nombre` vacío y un `sku` vacío.
- `contextos/producto/aplicacion/src/` tiene los cinco casos de uso, un fichero cada uno, con
  tests unitarios contra un repositorio doblado.
- `contextos/producto/rest/src/rutas.rs` tiene los cinco endpoints. Sus tests usan el
  `OpenApiService` real con casos de uso doblados.
- `presentacion/cableado/` y `presentacion/api/src/generado/bootstrap.rs` lo cablean todo. Nunca
  los editas.

<Aside type="tip">
Ejecuta `git diff` tras cualquier comando `puerto generar`. Ahí está cada cambio que hizo, ya
formateado.
</Aside>
