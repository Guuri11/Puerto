# Puerto vs. `document-api` — Comparison & Extraction Plan

> **Puerto** (`crates/cli`, v0.9.1) — the generator.
> **`document-api`** (`nexe/projects/nexe-document/document-api`) — a production backend
> **written entirely by hand, not generated by Puerto**: 60k LOC, 22 workspace crates, 1170 tests,
> 10 bounded contexts.
>
> **The relationship between the two is a shared ancestor, not a lineage.** Both adapt the same
> source conventions — `digitalia-dev/ant_backend` (Puerto: `PLAN.md:795`; document-api:
> "Adaptado de ant_backend" in six rules files). Neither derives from the other.
>
> Read as: **the same author's hand-written reference implementation vs. what the generator
> actually emits.** `document-api` is therefore the closest thing that exists to a *specification*
> for Puerto's output — it is what gets written by hand when Puerto is not in the loop. Every gap
> below is something written by hand, every time, that the generator does not provide.
>
> Comparison method: generated a real project with `puerto new --db` + `generate scaffold` and
> diffed its shape against `document-api`'s equivalent files, not against its docs.

---

## 1. Where they already agree

These agreements are **not independent evidence** — both projects adapt the same `ant_backend`
conventions, so shared shape is expected by construction. What they do show is that Puerto's
generator faithfully reproduces the target conventions:

| Convention | Puerto | `document-api` |
|---|---|---|
| Dependency rule `Presentation → Infrastructure → Application → Domain` | ✅ | ✅ |
| Whole module tree inline in `lib.rs`, **no `mod.rs`** | ✅ (patchers do it) | ✅ |
| `Model::new(props)` validates / `from_repository()` bypasses | ✅ | ✅ |
| Errors as `thiserror` with machine-readable codes (`entity.not_found`) | ✅ | ✅ |
| Repository trait as a port in domain, adapter in infrastructure | ✅ | ✅ |
| Value objects with private inner + `new() -> Result` | ✅ | ✅ |
| API First: `routes.rs` / `dto.rs` / `responses.rs` / `error_mapper.rs` per context | ✅ | ✅ |
| Poem OpenAPI + `ApiTags` | ✅ | ✅ |
| `mockall` on ports, gated by `#[cfg(any(test, feature = "test-utils"))]` | ✅ | ✅ |
| Object Mother for test fixtures | ✅ | ✅ |
| Domain never exposed in DTOs (`from_domain`) | ✅ | ✅ |
| `no unwrap()/expect()` in generated production code | ✅ | ✅ |

> **Correction (2026-10-10):** an earlier version of this table listed "Logger abstraction
> (`LoggerTrait` port + tracing adapter)" as shared. It is not: `document-api` has **no** logger
> port — its `architecture.md` says *"logging with `tracing::info!`/`warn!`/`error!` directly, no
> injected logger nor `Logger` port"*, and 54 files in `business/` call `tracing::` directly. See §6.6.

**What this is worth, stated honestly.** It is *not* proof that "a Puerto project scaled to 60k LOC"
— no Puerto project did. It is weaker but still useful evidence: writing by hand, at 60k LOC, with
total freedom to deviate, the same author kept these conventions instead of abandoning them. The
skeleton Puerto emits is one somebody actually lives with at scale. What is missing is everything
that gets added *around* it — and since document-api never started from Puerto's output, the list
below is not "what a Puerto project eventually needs" but something more direct: **the work its own
author does by hand on every project, which the generator could be doing.**

## 2. The structural divergences

### 2.1 Entity vs. bounded context

| | Puerto | `document-api` |
|---|---|---|
| Unit of generation | **entity** (`Product`) | **bounded context** (`intake`) |
| Directory | `domain/product/` | `domain/intake/` containing `IncomingItem`, `ProcessedEmail`, `ProcessedScanFile`, … |
| Files | `model.rs`, `errors.rs`, `repository.rs`, `use_cases/` | + `events.rs`, `unit_of_work.rs`, `value_objects.rs`, `formats.rs`, `media.rs`, `README.md` |

Puerto assumes **one aggregate = one directory = one CRUD**. `document-api` groups several
aggregates under one context with a shared error enum, shared events and one UoW.

Puerto's model is the right default (it is what a beginner needs), but there is no path from it to
the other: `puerto generate scaffold Product` inside an existing `intake` context is not expressible.
→ **T-21**

### 2.2 CRUD vs. intention-revealing use cases

Puerto generates `create/get/list/update/delete_product`. `document-api` has
`register_incoming_item`, `ingest_email_item`, `check_period_completeness`,
`detect_numbering_gaps`, `mark_unsupported`. Not one context has a generic `update_*`.

CRUD is the correct scaffold-a-demo default, but Puerto currently makes CRUD the *only* shape:
`generate use-case` exists, yet the 5 CRUD use cases are always created first and the anemic
`update_entity(all fields)` shape is what users start from. Consider `--no-crud` (domain + one
named use case) as the "I know what I'm doing" path. → **T-22**

### 2.3 Writes: repository vs. Unit of Work + events

This is the single biggest gap.

```rust
// Puerto — application/product/create_product.rs
let entity = Product::new(props)?;
self.repository.save(&entity).await?;      // bare repository write
Ok(entity)
```

```rust
// document-api — application/intake/register_incoming_item.rs
let item = IncomingItem::new(props)?;
let event = IntakeEvent::DocumentReceived(item.clone()).into_domain_event();
let mut uow = self.uow_factory.begin(&params.tenant_id).await?;
uow.save_incoming_item(&item).await?;
uow.save_domain_event(&event).await?;      // outbox row, same transaction
uow.commit().await?;                        // atomic
```

`document-api`'s rule (`.claude/rules/event-driven.md`): **every aggregate write emits a
`DomainEvent`, persisted in the same transaction (outbox), relayed to NATS JetStream by a worker,
consumed idempotently elsewhere.** No write use case takes a bare repository.

Puerto has no concept of: domain events, UoW, outbox table, event bus, consumers, dead letters.
A project that starts on Puerto and later needs events must retrofit the UoW port into every
existing write use case — precisely the refactor Puerto exists to avoid. → **T-23** (biggest item)

### 2.4 Multi-tenancy and typed IDs

```rust
// Puerto
pub struct Product { pub id: Uuid, … }
async fn find_by_id(&self, id: Uuid) -> …

// document-api
newtype_id!(TenantId); newtype_id!(IncomingItemId); newtype_id!(ClientCompanyId);
pub struct IncomingItem { pub id: IncomingItemId, pub tenant_id: TenantId, … }
async fn find_by_id(&self, tenant: &TenantId, id: &IncomingItemId) -> …
```

Two things Puerto lacks:

1. **Newtype IDs.** Raw `Uuid` everywhere means `find_by_id(company_id)` compiles when you meant
   `product_id`. A 20-line `macro_rules! newtype_id` makes it a compile error. Cheap, high value,
   fits Puerto's existing VO machinery. → **T-24**
2. **Tenant scoping.** `document-api` threads `TenantId` through every query, plus Postgres RLS
   (`0007_rls.sql`, `tenant_scope::begin_scoped`) and a mandatory integration test per repository
   asserting tenant A cannot read tenant B's rows. Puerto generates none of this. Multi-tenancy is
   the kind of decision that must be made at scaffold time — retrofitting it means rewriting every
   query, every repository test and every route. → **T-25**

### 2.5 Presentation DI: concrete vs. trait objects

```rust
// Puerto — presentation/src/api/product/routes.rs
pub struct ProductApi {
    pub create_product: Arc<CreateProductUseCaseImpl>,   // concrete application type
}

// document-api — presentation/rest-api/src/api/intake/routes.rs
pub struct IntakeApi {
    upload_document: Option<Arc<dyn UploadDocumentUseCase>>,   // port
}
```

Puerto's own `.claude/rules/architecture.md` says *"Dependencies injected as `Arc<dyn Trait>` —
never concrete types"*, and the generated application layer honours it. The **presentation layer
violates it**: routes depend on `business::application::*::Impl`, so a route cannot be unit-tested
with a mocked use case. `document-api` has 5 route tests in `intake/routes.rs` alone; Puerto
generates **0 tests in presentation and 0 in infrastructure**. → **T-26**

### 2.6 Reads: no pagination

`find_all() -> Vec<Product>` is unbounded. `document-api` has `PageRequest` (clamps `limit` to
`MAX_LIMIT = 200` in a VO with private fields, so no route can bypass it) and `PaginatedResult<T>`,
both in `domain/common/`. Puerto's `list_*` endpoint will happily return a million rows. → **T-27**

### 2.7 Error taxonomy

`document-api` splits it in two: a shared `RepositoryError` (`NotFound`, `Persistence`,
`Duplicated`, `DatabaseError`) that infrastructure maps driver errors onto (sqlx `23505` →
`Duplicated` via `error::map_sqlx_error`), plus per-context errors with `From<RepositoryError>`.
Puerto folds everything into one per-entity enum whose `Duplicate` variant **is never returned by
anything** — nothing maps Postgres error codes. Related to plan item T-05. → **T-28**

### 2.8 Infrastructure granularity & runtimes

| | Puerto | `document-api` |
|---|---|---|
| Crates | 3 (`business`, `infrastructure`, `presentation`) | 22 |
| Infrastructure | one crate | 15 crates (`persistence`, `event_bus`, `auth`, `config`, `object_storage`, `telemetry`, `shutdown`, `heartbeat`, 5 connectors…) |
| Binaries | 1 (`rest-api`) | 5 (`rest-api`, `worker`, `poller`, `watcher`, `cli`) |

3 crates is right for a starter. But there is no growth path: nothing in Puerto adds a second
binary (a worker consuming events, a CLI) or splits infrastructure into adapter crates. A real
backend needs a worker the moment it has events. → **T-29**

### 2.9 What `document-api` has that Puerto has no equivalent of at all

- **`scripts/check-architecture.sh`** — the dependency rule as an executable check (`cargo metadata`
  + `jq`, fails CI on a violation) instead of prose. Puerto documents the rule in three files and
  enforces it nowhere. This is *directly generatable* and cheap. → **T-30**
- **Mutation testing** (`cargo-mutants`) as a milestone gate on domain + application.
- **`README.md` per bounded context** (8 of them) explaining the domain in prose. Puerto generates
  0 READMEs — a generated project has no place where the *why* lives.
- **Centralized `tests/mothers.rs` + `tests/mocks.rs`** (360 + 2553 lines) with hand-written stubs
  that record calls, alongside `mockall`. Puerto generates one mother per entity and only `mockall`.
- **Test-DB isolation**: `DATABASE_TEST_URL` (never `DATABASE_URL`), no fallback — the test skips
  if unset. Born from finding test fixtures in a dev database. Puerto's generated tests use the
  single `DATABASE_URL`.
- **`fixtures/synthetic/`**, ADR references in code comments, `rust-toolchain.toml`, `Dockerfile`,
  `.dockerignore`, health/readiness endpoints, graceful shutdown, JWT auth, Prometheus metrics,
  Loki tracing.

## 3. Where Puerto is genuinely ahead

Not everything flows one way:

- **`puerto.toml` as a manifest.** `document-api` has no machine-readable description of its own
  contexts; every new aggregate is hand-written across ~15 files. Puerto's manifest + `generate
  bootstrap` is a real advantage — provided the code/manifest sync bug (plan T-04/T-08) is fixed.
- **Zero-manual-wiring DI.** `document-api` wires everything by hand in `main.rs`. Puerto generates
  it. This is the feature to protect above all others.
- **Generated tests.** A scaffolded entity ships with 20 tests (6 domain + 14 application) before
  the user writes a line. `document-api` earned its 1170 tests by hand.
- **VO ergonomics.** `sku:Sku:String!` generating VO + error variant + all four layer conversions
  has no equivalent in a hand-written project — there, every VO is written five times.
- **IDE snippets** (`puerto generate snippets`) — nothing similar exists in `document-api`.

## 4. The strategic question this comparison raises

The sharpest way to put the finding: **`document-api` could not have been built with Puerto, and
its author is the same person who wrote Puerto.** The skeleton would have been generated fine; the
UoW, the events, the tenancy, the pagination, the worker — all of that would have been hand-written
anyway, and from that moment on `puerto generate scaffold` becomes actively dangerous (it
overwrites, plan T-04) and `puerto.toml` goes stale (T-08). Puerto covers day 1 and steps aside at
day 30.

The useful counterfactual to design against is not "what does a Puerto project become" but
**"what would it have taken for document-api to have been started with Puerto and still be using it
today?"** That question produces the item list above, and it is answerable.

Three possible positionings, pick one deliberately:

**A. Starter generator** (today). Scaffold once, then the project leaves Puerto behind.
Cheap; explicitly caps the ceiling. Then the priority is only the P0/P1 bugs in the plan.

**B. Rails for DDD** — Puerto stays useful for the project's whole life: `puerto generate
event`, `puerto generate consumer`, `puerto generate worker`, `puerto destroy`, and generation is
non-destructive. This is where the items below point.

**C. Opinionated profiles** — `puerto new --profile minimal|events|multitenant` decides at project
creation which spine you get (bare repository vs. UoW+outbox; `Uuid` vs. newtype+tenant), and every
later generator respects the profile recorded in `puerto.toml`. Highest value, because these are
exactly the decisions that cannot be retrofitted cheaply, and it keeps the simple case simple.

**Recommendation: C**, implemented incrementally — `profile = "minimal"` is today's behaviour, so
it costs nothing to declare now (a `[project] profile` key in `puerto.toml` + validation), and each
later feature lands as a new profile rather than as a flag matrix. Do it **after** the P0 bugs:
a second spine multiplies the surface that currently has no compile coverage.

## 6. Conventions & AI rules (added 2026-10-10)

§1–5 compare *architecture*. This section compares the **instructions that steer the agents** and
the **tooling conventions** around the code — `.claude/rules/` (10 files, 1,400 lines, shared by the
whole `nexe-document` monorepo), the per-project `CLAUDE.md`, 46 ADRs in `docs/architecture/`, and
what Puerto ships for the same purpose: its own `AGENTS.md` + `.claude/rules/` (7 files), and the
three per-crate `AGENTS.md` it writes into every generated project.

### 6.1 Rules that are tied to a check, not just written down

`ai-collaboration.md` records the incident that shaped the whole rule set: *"seven modules were
implemented in the same working tree without a single intermediate commit. The rule already existed
in `CLAUDE.md` ('baby steps') but was not tied to anything verifiable — so it was not followed."*
From then on, every rule names the check that enforces it: Dependency Rule → `check-architecture.sh`;
baby steps → one atomic commit per piece, visible in `git log`; test quality → `cargo-mutants`.

Puerto has the same disease, and it is visible today:

- **The AI rules Puerto ships to generated projects have drifted from Puerto's own rules.** The
  generated `business/AGENTS.md`, `infrastructure/AGENTS.md` and `presentation/AGENTS.md` draw trees
  with `mod.rs` files — the exact thing `architecture.md` forbids ("No `mod.rs` files. Module
  hierarchy is declared inline in `lib.rs`"). An agent in a generated project is told to create
  them. Nothing tests those files.
- **"Spec exists in PLAN.md before implementation"** (workflow checklist) is checked by nothing.
- The 2026-10-10 review-fix session accumulated a WIP change plus ~20 fixes plus docs in one
  uncommitted tree — the same failure mode as the incident above.

→ **T-31**: a structural test asserting the generated `AGENTS.md` files never mention `mod.rs` and
name the real files; adopt "one atomic commit per fix" in `workflow.md`.

### 6.2 Generated projects have no entry point for Claude Code

Puerto's own repo does `CLAUDE.md` → `@AGENTS.md`, because Claude Code loads `CLAUDE.md`. A
generated project has **no root `CLAUDE.md` and no root `AGENTS.md`** — only the three per-crate
`AGENTS.md`. So for a Claude Code user, the generated project's rules are not loaded unless an agent
happens to open them. `document-api`'s `CLAUDE.md` is 20 lines and points to the rules it inherits.

→ **T-32**: generate a root `AGENTS.md` (architecture, dependency rule, TDD loop, `puerto` commands
for this project, "never hand-edit `generated/bootstrap.rs`") plus a one-line `CLAUDE.md` importing
it — the same pattern Puerto uses for itself.

### 6.3 Risk tiers: where human review goes

`ai-collaboration.md` splits code by **how forgiving the system is when it is wrong**. Tier 1
(silent, slow or expensive failure: tenant boundary, money arithmetic, dedup verdicts, auth guards,
destructive migrations) needs a human to read the whole diff, even with a green gate. Tier 2 (fails
loudly and reversibly: DTO-mapping handlers, adapters covered by real integration tests, docs)
trusts the gate. A piece touching both is Tier 1.

Puerto has no such calibration. Its natural Tier 1 is **anything that changes generated output in
existing projects or a public contract**: templates, `puerto.toml` schema, `bootstrap.rs` generation,
migration SQL, patchers that rewrite user files (`lib.rs`, `api.rs`, `routes.rs`). Tier 2: CLI
messages, docs, snippets. → **T-33** (docs only; also worth shipping a short version to generated
projects).

### 6.4 Decisions get an ADR

46 ADRs, cited from rules and from code comments (`ADR-0013`, `ADR-0030`…), each with the incident or
measurement behind it. Rule: *"when Claude makes a design decision based on unwritten context, it is
written down — as an ADR or a rule update — instead of living only in the code or the chat."*

Puerto's decisions live in `PLAN.md` (1,100+ lines, mixed spec and history) and in code comments.
The comments are good — they explain *why* (`"used to emit … (E0252)"`) — but there is no place to
find "why does Puerto do X". Candidates from 2026-10-10 alone: enum VOs implement `FromStr`; response
enums allow `large_enum_variant`; unique indexes are partial; `generate use-case` refuses existing
actions; SQL reserved words rejected only in `--db` projects. → **T-34**: `docs/adr/`, one file per
decision, start with these five.

### 6.5 Tooling conventions

| | `document-api` | Puerto repo | Puerto-generated project |
|---|---|---|---|
| `rust-toolchain.toml` | pinned `1.97` + rustfmt/clippy | ❌ | ❌ |
| `rustfmt.toml` | `max_width = 100` | ❌ (defaults) | ❌ |
| Edition | 2024 | 2024 | **2021** |
| `.cargo/config.toml` `SQLX_OFFLINE` | ✅ | — | ✅ (`--db`) |
| Dependency-rule check | `scripts/check-architecture.sh` | — | ❌ (T-30) |
| Mutation testing | `cargo-mutants`, actually used (85 caught / 1 missed, last run 2026-10-03) | ❌ | ❌ |
| Test DB | `DATABASE_TEST_URL`, skip if unset, dedicated container | `make test/db` (throwaway container) | `#[sqlx::test]` — throwaway DB per test |
| `//!` module docs explaining *why* | almost every file | most files | ❌ none |
| `README.md` per context | 8 | — | ❌ |

The toolchain pin matters more than it looks. The lints fixed on 2026-10-10 (`manual_inspect`,
`unnecessary_map_or`, `should_implement_trait`…) depend on the clippy version: without a pinned
toolchain a generated project's `make lint` passes or fails depending on whose machine runs it, and
Puerto's matrix only proves it for the toolchain of whoever ran `make test/full`.
→ **T-35**: generate `rust-toolchain.toml` (same version Puerto's matrix runs with) and edition 2024
(MSRV 1.85 is already Puerto's own).

Mutation testing fits Puerto itself well — `validation.rs`, `migration.rs` (timestamp arithmetic),
the type registry and the patchers are pure functions. → **T-36**: `make test/mutation` on Puerto;
later, generate the target into projects.

On test-DB isolation Puerto is **not** behind: `#[sqlx::test]` creates a throwaway database per test,
so fixtures never land in the dev database (the incident behind `document-api`'s ADR-0030). It does
need `CREATEDB` on the server behind `DATABASE_URL`, which deserves a line in the generated docs.

### 6.6 Code conventions that differ

- **Logging.** `document-api`: `tracing::` directly — `tracing` is already a facade, and it is
  testable without injection. Puerto: an injected `LoggerTrait`, which costs a `logger` field in
  every use case and repository, a `silent_logger()` mock helper in every test module, and an extra
  argument in every `bootstrap.rs` wiring. Neither is wrong, but `document-api`'s author chose the
  opposite at scale; worth an ADR either way (T-34). Changing it is a breaking change.
- **Error responses.** `document-api`: `ErrorResponse { name: "intake.not_found", … }` — the
  machine code is the `name`; validation → **422**, with 413/415 for size/format; mappers are
  exhaustive and **unit-tested**. Puerto: `name: "product_error"` (generic) with the code in
  `message`; validation → 400; no mapper tests. → **T-37**: put the code in `name`, use 422 for
  domain validation (400 stays for unparseable payloads, which poem already returns), generate one
  test per mapper arm. Breaking for API clients.
- **Health.** `document-api`: `/health` (liveness) **and** `/health/ready` (pings the DB; the module
  docs explain why a liveness-only probe reported a stack with Postgres down as healthy), plus
  graceful shutdown with a deadline. Puerto-generated projects have neither. → **T-38**: generate
  both probes (`ready` pings the pool when `--db`) and `run_with_graceful_shutdown`. Small.
- **Trait names.** `RegisterIncomingItemUseCase` vs Puerto's `CreateProductUseCaseTrait`. The Rust
  API guidelines avoid type-kind suffixes; low value, breaking — note only.
- **Use-case results.** `document-api` returns outcome enums (`RegistrationOutcome::Duplicate(…)`)
  where idempotency is a business concept; Puerto always returns the entity. Fits T-22.

### 6.7 Where Puerto is ahead on AI rules

- **Lean context.** Puerto's `CLAUDE.md` → `AGENTS.md` is ~200 lines. `nexe-document`'s root
  `CLAUDE.md` is 761 lines, ~66 KB of it a running status log ("M7 has a number since…") loaded into
  every session in every sub-project — it belongs in `docs/specs/README.md`, which it already
  references. (A lesson for `document-api`, not for Puerto.)
- **Tool-agnostic `AGENTS.md`** with `CLAUDE.md` as a one-line import: works for Codex and other
  agents too. (Undermined in generated projects by §6.2.)
- **Generation is under test.** After 2026-10-10 the matrix runs clippy and tests in every generated
  project, including a `--db` one against Postgres. `document-api` has no equivalent for "is the
  pattern we copy by hand still correct" — every new context re-derives it.
