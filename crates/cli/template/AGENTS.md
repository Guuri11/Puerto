# AI Agent Instructions

A Rust backend generated by [Puerto](https://github.com/Guuri11/Puerto): DDD + Hexagonal
(Ports & Adapters), three crates, REST API with poem-openapi. This file is the entry point for any
coding agent (`CLAUDE.md` imports it). Each crate has its own detail:
`business/AGENTS.md`, `infrastructure/AGENTS.md`, `presentation/AGENTS.md`.

## Architecture

```
presentation → infrastructure → business (application → domain)
```

Dependencies point inward only. `business` depends on no other crate of this workspace;
`infrastructure` never depends on `presentation`.

| Crate | Holds | Never |
|---|---|---|
| `business` | domain (models, value objects, errors, repository ports, use case traits) + application (use case impls) | imports a database driver, HTTP framework or adapter |
| `infrastructure` | adapters implementing the domain ports (in-memory or Postgres repositories) | contains business rules |
| `presentation` | HTTP: routes, DTOs, responses, error mapping, health probes, DI wiring | exposes a domain model in a response |

**The Puerto runtime.** What every Puerto project shares is not copied into it: it is a crate,
declared once in the root `Cargo.toml` (`[workspace.dependencies]`, on the same minor as the
`puerto` CLI) and inherited by each member with `{ workspace = true }`.

| Crate | Owns | Imported as |
|---|---|---|
| `puerto-core` | `RepositoryError` (what every repository port fails with), `PageRequest` / `Page<T>` (paged lists, limit capped at 100) | `use puerto_core::{Page, PageRequest, RepositoryError};` |
| `puerto-web` | the server (`App`: tracing, CORS, graceful shutdown), `Config` (read from the environment and `.env`), the `/health` and `/health/ready` probes, `ErrorResponse` | `presentation` only — `main.rs`, `generated/bootstrap.rs`, `use puerto_web::ErrorResponse;` |
| `puerto-sqlx` (`--db` projects) | the Postgres pool, migrations at startup, the readiness `ping`, `map_sqlx_error` (driver error → `RepositoryError`) | `infrastructure` only — re-exported by `infrastructure/src/db.rs`, which keeps the project's `MIGRATOR` |

`puerto-core` depends on nothing but `thiserror`, so the domain may use it; `puerto-web` carries
poem and stays in `presentation`; `puerto-sqlx` carries sqlx and stays in `infrastructure`. Do not
copy their code into the project; upgrade them with the `puerto` CLI (`puerto validate` warns when
they drift apart). Your own middleware and routes go in `presentation/src/app.rs`, which no
generator touches.

**Modules are declared inline in each crate's `lib.rs`** (nested `pub mod {}` blocks). There are
no `mod.rs` files: adding a use case is one line in `lib.rs` plus its file.

## `puerto.toml` is the source of truth

It describes every entity, its fields and use cases, and the project's features (`db`, `web`,
`events`, `auth`). The `puerto` CLI generates the code and the wiring from it; `puerto validate`
checks the two still agree. `puerto list` prints what it declares, `puerto <command> --help` says
everything below in more detail.

| Command | What it writes |
|---|---|
| `puerto generate scaffold <Name> [-- fields…]` | every layer of a CRUD entity (create, get, list, update, delete) + its screens with `web/` + its table migration with `db` |
| `puerto generate domain <Name> [-- fields…]` | the domain layer only, and the entity in `puerto.toml` — then `application`, `repository`, `presentation` (and `web`), one layer at a time |
| `puerto generate use-case <Entity> <action>` | one more use case: its trait + mock, its impl to fill in (see below), a field on `<Entity>Api` |
| `puerto generate value-object <Name> <type>` | a shared value object (`[[value_object]]`), reusable by every entity |
| `puerto generate migration <name>` | an empty SQL migration (`db` projects) |
| `puerto generate bootstrap` | rewires `generated/bootstrap.rs` (and `web/`'s generated files) from `puerto.toml` |
| `puerto generate web <Name>` | an entity's screens alone (`web/` projects) |
| `puerto generate event <Entity> <name>` | a custom domain event (`events` projects) |
| `puerto generate consumer <name> --on <event_type>[,…]` | a worker consumer (`events` projects) |
| `puerto generate mail <name> [-- fields…] [--on <event_type> --to <field>]` | a mail: its port, its templates, its SMTP adapter; with `--on`, the worker sends it |
| `puerto generate snippets` | editor snippets for the patterns below (Zed, VS Code) |
| `puerto validate` | checks names, types, and that the manifest and the code agree |

In an auth project `scaffold` also takes `--public <use_case>[,…]` (no token needed) and
`--role <use_case>=<role>[,…]` (see the Auth section).

### Fields

Fields go after `--`, one argument each, no quoting:

| Argument | Field |
|---|---|
| `title:String`, `price:i64`, `active:bool`, `ratio:f64`, `owner_id:Uuid` | a primitive |
| `price:i64!` | `!` at the end: unique (a partial unique index in Postgres; not on `opt`/`vec`) |
| `summary:opt:String` | `Option<String>` — nullable |
| `tags:vec:String` | `Vec<String>` (`String` or `i64`) |
| `published_at:DateTime` | `DateTime<Utc>` (`opt:DateTime` too) |
| `meta:map` | `HashMap<String, String>` — a `JSONB` column |
| `name:Name:String` | a value object `Name` wrapping a primitive: validated once, in `Name::new` |
| `middle_name:MiddleName:opt:String` | an optional value object |
| `label:Label:vec:String` | a list of value objects |
| `status:Status:enum:Draft/Published` | an enum value object (`"Draft".parse::<Status>()`) |
| `email:Email` | a shared value object declared with `generate value-object` (type inferred) |

Prefer a value object to a bare primitive when the field has a rule: the rule then lives in one
place, and an invalid value is an error code (`product.invalid_name`, `422`) everywhere.

### Generated vs yours

| | Files | Change them by |
|---|---|---|
| **Rewritten on every run** — never hand-edit | `presentation/src/generated/bootstrap.rs`, `presentation/src/api/tags.rs`, `business/src/domain/<entity>/events.rs`, `worker/src/generated/registry.rs`, `web/src/presentation/core/generated/*`, `web/src/infrastructure/http/schema.d.ts`, `docs/api/openapi.json` | editing `puerto.toml` or the code they are derived from, then the command that writes them (`generate bootstrap`, `make web/sync`) |
| **The entity's files** — yours, but `scaffold --force` rewrites them | the CRUD use cases, model, errors, repository, routes, DTOs, mappers, Mother, screens of one entity | editing them; `--force` only while they are still what the generator wrote |
| **Patched** — a line added, the rest kept | each crate's `lib.rs`, `presentation/src/api.rs`, `routes.rs` (`<Entity>Api` fields), `worker/src/consumers.rs`, `puerto.toml` | editing them freely; keep the lines Puerto added |
| **Written once** — yours from the start | `presentation/src/app.rs` (your middleware and routes), `web/src/presentation/core/routes.tsx` (your screens), the impl of a `generate use-case`, consumers, mails and their templates, migrations, the auth files | editing them |

### Changing an entity's fields

- **The code is still what the generator wrote:** change the `[[entity]]` block in `puerto.toml`
  (or pass the new field list) and run `puerto generate scaffold <Name> --force`. Use cases added
  with `generate use-case` survive; any other hand-written change to the entity's files is lost.
- **In a `--db` project the table migration is never rewritten** (it may already be applied). Not
  applied anywhere yet: edit that `create_<entity>_table` migration. Applied: add
  `puerto generate migration add_<field>_to_<plural>` with the `ALTER TABLE`, then
  `make sqlx/migrate && make sqlx/prepare`.
- **The code is already yours:** add the field by hand through every layer — model and Props,
  params, the Mother, the row and its conversions, the DTOs, the screens — with a migration, and
  update `[[entity.fields]]` so `puerto.toml` keeps describing the code.

## Working with Puerto

Generate first, then write the business rules test first. Never write wiring by hand: if
`bootstrap.rs`, a `lib.rs` module tree or `<Entity>Api` needs a line, a command writes it.

1. **Model it in the generator.** A new entity: `puerto generate scaffold <Name> -- …` with its
   fields, value objects and enums. One more operation on an entity:
   `puerto generate use-case <Entity> <action>`.
2. **List the scenarios** before code: the happy path, empty and invalid input, boundaries, state
   transitions, and the regression a bug fix needs.
3. **Red.** A scaffolded entity already has tests for what it generated; add yours next to them.
   `generate use-case` leaves the impl as `todo!()`, placeholder `Params` (`name: String`) and a
   test marked `#[ignore = "write this test"]` in `business/src/application/<entity>/<action>.rs`:
   remove the `ignore`, write the test, watch it fail.
4. **Green.** The domain first: invariants in the model's `new` or a value object, then `Params`
   and the trait (`domain/<entity>/use_cases/<action>.rs`), then the impl in `application/`.
5. **The endpoint, API first.** `generate use-case` puts the use case on `<Entity>Api` but adds no
   route: write `dto.rs`, `responses.rs`, the `error_mapper.rs` arm for any new error (with its
   test), then the handler in `routes.rs` and one route test per status
   (`presentation/AGENTS.md`).
6. **Sync and check.** `make web/sync` after any route or DTO change in a project with `web/`,
   then the checks below; one commit.

## Frontend (`web/`)

A React + daisyUI app on Bun that talks to the API under `/api`. It follows the same Dependency
Rule as the crates (`domain` ← `application` ← `infrastructure` ← `presentation`), checked by
`make web/lint`. Its rules — layers, generated files, where use cases go — are in `web/AGENTS.md`.

The OpenAPI spec is the contract between the two halves: `docs/api/openapi.json`, exported by a
test in `bootstrap.rs`. **After a scaffold and after touching a route or a DTO, run
`make web/sync`** (it re-exports the spec, regenerates the frontend's wire types and formats
`web/`) and commit both. Until then `make test` fails — that failure is the drift check.
`puerto generate scaffold` writes a CRUD entity's screens too; `puerto generate web <Name>` writes
them alone.

## Conventions

- **TDD.** Write the failing test first, then the minimum code. Test names:
  `should_<expected_behaviour>_when_<scenario>`, with `// Arrange` / `// Act` / `// Assert`.
- **Errors are machine-readable codes** (`product.not_found`,
  `product.validation_error.title_empty`), never sentences. The API returns them in
  `ErrorResponse.name`; domain validation failures are `422`.
- **Logging:** `tracing::info!` / `warn!` / `error!` directly — no injected logger. A use case logs
  `<use_case>: start` and `<use_case>: done`; never log request payloads (they are user data).
- **No `unwrap()` / `expect()`** outside tests.
- **API First:** change `routes.rs` + `dto.rs` (the contract) before the implementation.

## Check before you are done

```bash
puerto validate  # the manifest and the code agree
make test        # unit + integration tests (and web/'s, when present)
make lint        # clippy --all-targets -D warnings — the toolchain is pinned in rust-toolchain.toml
make format      # rustfmt check — `make format/fix` applies it
```

- **With `web/`:** `make web/sync` after a scaffold or any route / DTO change, and commit what it
  wrote — until then `make test` fails on the drift.
- **In a `--db` project:** `make docker-compose/up` before `make test` (the `#[sqlx::test]`s need
  Postgres), and `make sqlx/prepare` after changing a query or a migration — commit `.sqlx/`.

`rust-toolchain.toml` pins the Rust version: clippy gains lints between releases, so a pinned
toolchain is what makes `make lint` give the same answer on every machine.

## How to work here

**Make one commit per piece.** Finish one use case (or one fix), get `make test` and `make lint`
green, commit, then start the next. A rule like "small steps" that is not tied to anything
checkable does not get followed; a commit per piece is visible in `git log`.

**Where a human must read the diff** — calibrate by how forgiving the system is when the code is
wrong:

- **Tier 1 — fails silently, slowly or expensively.** A green test suite is not enough; a person
  reads the whole diff before it is committed: SQL migrations (above all destructive ones),
  anything touching money or other arithmetic the business relies on, authentication and
  authorization checks, uniqueness / deduplication rules, data that crosses a tenant or customer
  boundary.
- **Tier 2 — fails loudly and reversibly.** The checks above are enough: DTO ↔ domain mapping,
  adapters covered by real integration tests, read-only queries, docs.

A change touching both tiers is Tier 1.

**Write decisions down.** When a design decision rests on context that is not in the code, record
it — an ADR under `docs/adr/` or an update to these files — so the next session inherits the
reason instead of re-deriving it or undoing it.
