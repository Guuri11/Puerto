# AI Agent Instructions

A Rust backend generated by [Puerto](https://github.com/Guuri11/Puerto): DDD + Hexagonal
(Ports & Adapters), one crate per context and layer, REST API with poem-openapi. This file is the
entry point for any coding agent (`CLAUDE.md` imports it). The detail is next to the code:
`contextos/AGENTS.md`, `presentacion/AGENTS.md`.

## Architecture

```
nucleo/                 shared value objects — no I/O
contextos/<c>/          one context per entity of puerto.toml, four crates each:
  dominio/              → dominio_<c>      models, value objects, errors, repository ports
  aplicacion/           → aplicacion_<c>   one file per use case: params, trait, impl, tests
  infraestructura/      → infra_<c>        adapters: in-memory or Postgres repositories
  rest/                 → rest_<c>         HTTP: routes, DTOs, responses, error mapping
presentacion/
  cableado/             GENERATED: builds every context's repositories and use cases
  api/                  the binary: health probes, the generated bootstrap, your `app.rs`
migraciones/, migrador/ the SQL of the whole database and its one `MIGRADOR` (`--db` projects)
```

Dependencies point inward only, and Cargo enforces them: `rest → aplicacion → dominio → nucleo`,
`infraestructura → dominio`; only `presentacion/*` depends on `infra_*`. A reference between
entities is a dependency between their domain crates, so references never form a cycle.

| Crate | Holds | Never |
|---|---|---|
| `dominio_<c>` | the model, its id type, value objects, errors, the repository port | imports a database driver, HTTP framework or adapter |
| `aplicacion_<c>` | the use cases — each one's contract and its implementation | knows about HTTP or storage |
| `infra_<c>` | adapters implementing the domain ports | contains business rules |
| `rest_<c>` | routes, DTOs, responses, error mapping | exposes a domain model in a response |

**The Puerto runtime.** What every Puerto project shares is not copied into it: it is a crate,
declared once in the root `Cargo.toml` (`[workspace.dependencies]`, on the same minor as the
`puerto` CLI) and inherited by each member with `{ workspace = true }`.

| Crate | Owns | Imported by |
|---|---|---|
| `puerto-nucleo` | `ErrorRepositorio` (what every repository port fails with), `PeticionPagina` / `Pagina<T>` (paged lists, limit capped at 100) | every crate: `use puerto_nucleo::{Pagina, PeticionPagina, ErrorRepositorio};` |
| `puerto-web` | the server (`App`: tracing, CORS, graceful shutdown), `Config` (read from the environment and `.env`), the `/health` and `/health/ready` probes, `RespuestaError` | `rest_*` and `presentacion/api` |
| `puerto-sqlx` (`--db` projects) | the Postgres pool, migrations at startup, the readiness `ping`, `mapear_error_sqlx` (driver error → `ErrorRepositorio`) | `infra_*` and the binaries |

`puerto-nucleo` depends on nothing but `thiserror`, so the domain may use it; `puerto-web` carries
poem and stays in the REST crates and the binary; `puerto-sqlx` carries sqlx and stays in the
infrastructure crates and the binaries. Do not copy their code into the project; upgrade them with
the `puerto` CLI (`puerto validar` warns when they drift apart). Your own middleware and routes go
in `presentacion/api/src/app.rs`, which no generator touches.

**Each crate's `lib.rs` is flat**: one `pub mod` per file, no `mod.rs`. Adding a use case is one
line in the application crate's `lib.rs` plus its file — `puerto generar caso-de-uso` writes both.

## `puerto.toml` is the source of truth

It describes every entity, its fields and use cases, and the project's features (`db`, `web`,
`events`, `auth`). The `puerto` CLI generates the code and the wiring from it; `puerto validar`
checks the two still agree. `puerto listar` prints what it declares, `puerto <command> --help` says
everything below in more detail.

| Command | What it writes |
|---|---|
| `puerto generar scaffold <Name> [-- fields…]` | every layer of a CRUD entity (create, get, list, update, delete) + its table migration with `db` |
| `puerto generar dominio <Name> [-- fields…]` | the domain layer only, and the entity in `puerto.toml`; then `puerto generar aplicacion <Name>`, `puerto generar repositorio <Name>`, `puerto generar presentacion <Name>` — one layer at a time, each checking the one before |
| `puerto generar caso-de-uso <Entity> <action>` | one more use case: its file — trait + mock, the impl to fill in (see below) — and a field on `<Entity>Api` |
| `puerto generar objeto-valor <Name> <type>` | a shared value object (`[[objeto_valor]]`), reusable by every entity |
| `puerto generar migracion <name>` | an empty SQL migration (`db` projects) |
| `puerto generar bootstrap` | rewires `presentacion/cableado` and `generado/bootstrap.rs` from `puerto.toml` |
| `puerto generar evento <Entity> <name>` | a custom domain event (`events` projects) |
| `puerto generar consumidor <name> --tras <event_type>[,…]` | a worker consumer (`events` projects) |
| `puerto generar correo <name> [-- fields…] [--tras <event_type> --para <field>]` | a mail: its port, its templates, its SMTP adapter; with `--tras`, the worker sends it |
| `puerto generar snippets` | editor snippets for the patterns below (Zed, VS Code) |
| `puerto validar` | checks names, types, and that the manifest and the code agree |

In an auth project `scaffold` also takes `--publico <use_case>[,…]` (no token needed) and
`--rol <use_case>=<role>[,…]` (see the Auth section).

### Fields

Fields go after `--`, one argument each, no quoting:

| Argument | Field |
|---|---|
| `title:String`, `price:i64`, `active:bool`, `ratio:f64`, `owner_id:Uuid` | a primitive |
| `price:i64!` | `!` at the end: unique (a partial unique index in Postgres; not on `opt`/`vec`) |
| `summary:opt:String` | `Option<String>` — nullable |
| `tags:vec:String` | `Vec<String>` (`String` or `i64`) |
| `published_at:DateTime` | `DateTime<Utc>` (`opt:DateTime` too) |
| `meta:map` | `HashMap<String, String>` — a `JSONB` column |
| `name:Name:String` | a value object `Name` wrapping a primitive: validated once, in `Name::new` |
| `middle_name:MiddleName:opt:String` | an optional value object |
| `label:Label:vec:String` | a list of value objects |
| `status:Status:enum:Draft/Published` | an enum value object (`"Draft".parse::<Status>()`) |
| `email:Email` | a shared value object declared with `generar objeto-valor` (type inferred) |
| `customer_id:ref:Customer` | a reference: the `CustomerId` of a `Customer` scaffolded before (`!`: one-to-one) |
| `reviewer_id:ref:opt:Customer` | an optional reference |

Prefer a value object to a bare primitive when the field has a rule: the rule then lives in one
place, and an invalid value is an error code (`product.invalid_name`, `422`) everywhere.

An entity refers to another by its id, never by holding it: a use case that needs the customer asks
the customer's repository. With a database the column is a foreign key, and a write naming a
customer that does not exist answers `422` `order.validation_error.customer_id_not_found`.
Deleting a customer (a soft delete) leaves its orders pointing at it. The list filters by each
reference: `GET /orders?customerId=…` (`ListOrdersParams { customer_id }`, `OrderFilter` in the
repository port). On the web the reference is a `<select>` of customers and a link on the detail.

### Generated vs yours

| | Files | Change them by |
|---|---|---|
| **Rewritten on every run** — never hand-edit | `presentacion/cableado/` (its `Cargo.toml` too), `presentacion/api/src/generado/bootstrap.rs`, `contextos/<c>/dominio/src/eventos.rs`, `presentacion/worker/src/generado/registro.rs` | editing `puerto.toml`, then the command that writes them (`generar bootstrap`, `generar evento`, `generar consumidor`) |
| **The entity's files** — yours, but `scaffold --forzar` rewrites them | the four crates of one context: the CRUD use cases, model, errors, repository, routes, DTOs, mappers, Mother — and their `Cargo.toml` and `lib.rs` | editing them; `--forzar` only while they are still what the generator wrote |
| **Patched** — a line added, the rest kept | the root `Cargo.toml` (members, `[workspace.dependencies]`), `presentacion/api/Cargo.toml` and `presentacion/worker/Cargo.toml` (a context's crate), the application crate's `lib.rs`, `rutas.rs` (`<Entity>Api` fields), `presentacion/worker/src/consumidores.rs`, `puerto.toml` | editing them freely; keep the lines Puerto added |
| **Written once** — yours from the start | `presentacion/api/src/app.rs` (your middleware and routes), the impl of a `generar caso-de-uso`, consumers, mails and their templates, migrations, the auth files | editing them |

### Changing an entity's fields

- **The code is still what the generator wrote:** change the `[[entidad]]` block in `puerto.toml`
  (or pass the new field list) and run `puerto generar scaffold <Name> --forzar`. Use cases added
  with `generar caso-de-uso` survive; any other hand-written change to the entity's files is lost.
- **In a `--db` project the table migration is never rewritten** (it may already be applied). Not
  applied anywhere yet: edit that `create_<entity>_table` migration. Applied: add
  `puerto generar migracion add_<field>_to_<plural>` with the `ALTER TABLE`, then
  `make sqlx/migrate && make sqlx/prepare`.
- **The code is already yours:** add the field by hand through every layer — model and Props,
  params, the Mother, the row and its conversions, the DTOs, any screen — with a migration, and
  update `[[entidad.campos]]` so `puerto.toml` keeps describing the code.

## Working with Puerto

Generate first, then write the business rules test first. Never write wiring by hand: if
the wiring, a `lib.rs` or `<Entity>Api` needs a line, a command writes it.

1. **Model it in the generator.** A new entity: `puerto generar scaffold <Name> -- …` with its
   fields, value objects and enums. One more operation on an entity:
   `puerto generar caso-de-uso <Entity> <action>`.
2. **List the scenarios** before code: the happy path, empty and invalid input, boundaries, state
   transitions, and the regression a bug fix needs.
3. **Red.** A scaffolded entity already has tests for what it generated; add yours next to them.
   `generar caso-de-uso` leaves the impl as `todo!()`, placeholder `Params` (`name: String`) and a
   test marked `#[ignore = "write this test"]` in `contextos/<c>/aplicacion/src/<action>.rs`:
   remove the `ignore`, write the test, watch it fail.
4. **Green.** The domain first: invariants in the model's `new` or a value object
   (`contextos/<c>/dominio/`), then the use case's `Params`, trait and impl — one file.
5. **The endpoint, API first.** `generar caso-de-uso` puts the use case on `<Entity>Api` but adds no
   route: write `dto.rs`, `respuestas.rs`, the `errores.rs` arm for any new error (with its
   test), then the handler in `rutas.rs` and one route test per status
   (`contextos/AGENTS.md`).
6. **Check.** Everything in *Check before you are done*, then one commit.

## Frontend (`web/`)

A React + daisyUI app on Bun that talks to the API under `/api`. It follows the same Dependency
Rule as the crates (`domain` ← `application` ← `infrastructure` ← `presentation`), checked by
`make web/lint`. Its rules — layers, generated files, where use cases go — are in `web/AGENTS.md`.

The OpenAPI spec is the contract between the two halves: `docs/api/openapi.json`, exported by a
test in `generado/bootstrap.rs`. **After a scaffold and after touching a route or a DTO, run
`make web/sync`** (it re-exports the spec, regenerates the frontend's wire types and formats
`web/`) and commit both. Until then `make test` fails — that failure is the drift check.
`puerto generar scaffold` writes a CRUD entity's screens too; `puerto generar web <Name>` writes
them alone.

## Conventions

- **TDD.** Write the failing test first, then the minimum code. Test names:
  `should_<expected_behaviour>_when_<scenario>`, with `// Arrange` / `// Act` / `// Assert`.
- **Errors are machine-readable codes** (`product.not_found`,
  `product.validation_error.title_empty`), never sentences. The API returns them in
  `RespuestaError.codigo`; domain validation failures are `422`.
- **Logging:** `tracing::info!` / `warn!` / `error!` directly — no injected logger. A use case logs
  `<use_case>: start` and `<use_case>: done`; never log request payloads (they are user data).
- **No `unwrap()` / `expect()`** outside tests.
- **API First:** change `rutas.rs` + `dto.rs` (the contract) before the implementation.

## Check before you are done

```bash
puerto validar  # the manifest and the code agree
make test        # unit + integration tests
make lint        # clippy --all-targets -D warnings — the toolchain is pinned in rust-toolchain.toml
make format      # rustfmt check — `make format/fix` applies it
```

<!-- web -->
- **With `web/`:** `make web/sync` after a scaffold or any route / DTO change, and commit what it
  wrote — until then `make test` fails on the drift. `make test` and `make lint` run the
  frontend's checks too.
<!-- /web -->
- **In a `--db` project:** `make docker-compose/up` before `make test` (the `#[sqlx::test]`s need
  Postgres), and `make sqlx/prepare` after changing a query or a migration — commit `.sqlx/`.

`rust-toolchain.toml` pins the Rust version: clippy gains lints between releases, so a pinned
toolchain is what makes `make lint` give the same answer on every machine.

## How to work here

**Make one commit per piece.** Finish one use case (or one fix), get `make test` and `make lint`
green, commit, then start the next. A rule like "small steps" that is not tied to anything
checkable does not get followed; a commit per piece is visible in `git log`.

**Where a human must read the diff** — calibrate by how forgiving the system is when the code is
wrong:

- **Tier 1 — fails silently, slowly or expensively.** A green test suite is not enough; a person
  reads the whole diff before it is committed: SQL migrations (above all destructive ones),
  anything touching money or other arithmetic the business relies on, authentication and
  authorization checks, uniqueness / deduplication rules, data that crosses a tenant or customer
  boundary.
- **Tier 2 — fails loudly and reversibly.** The checks above are enough: DTO ↔ domain mapping,
  adapters covered by real integration tests, read-only queries, docs.

A change touching both tiers is Tier 1.

**Write decisions down.** When a design decision rests on context that is not in the code, record
it — an ADR under `docs/adr/` or an update to these files — so the next session inherits the
reason instead of re-deriving it or undoing it.
